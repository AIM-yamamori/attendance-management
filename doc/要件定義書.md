## 1. 概要

### 1.1 目的

現在Excelファイル（勤務実績管理表）を個人ごと・月ごとに作成し、OneDrive上で管理している勤怠管理業務を、Webシステム化する。ユーザーはブラウザから勤怠を入力・閲覧でき、管理者（admin）は全ユーザーの勤怠を閲覧・PDF出力・編集ロック管理できるようにする。

### 1.2 対象システムの範囲

- フロントエンド：ブラウザで動作するWebアプリケーション
- バックエンド：勤怠データの保存・検証・PDF出力・ロック制御を担うAPI/サーバー
- データストア：OneDrive上のExcelファイル群（ユーザー×月ごとのファイル）を実データベースとして利用

### 1.3 想定技術構成（案）

| 方式 | 内容 |
|---|---|
| 案A | Streamlit（Python）で一体型Webアプリを構築。フロント・バック分離ではなく単一Pythonアプリ内で完結 |
| 案B | HTML/JS（フロントエンド）＋ Python API（バックエンド、例：FastAPI/Flask）の分離構成 |

どちらの案を採用するかは非機能要件・開発体制次第。本書では両案に対応できるよう、機能要件はUIとロジックを分離して記述する。

> **要確認事項**：Streamlit案・分離構成案のどちらを採用するか、後述の「14. 未確定事項・要確認事項」にまとめて記載。

## 2. 用語定義

| 用語 | 説明 |
|---|---|
| 勤務実績管理表 | 1ユーザー・1ヶ月分の勤怠を記録するExcelファイル（アップロードされたサンプルが原本） |
| テンプレート | 新規月次ファイルを生成する際の元となるExcelファイル（`原本`シートを使用） |
| ロック | 対象月の勤怠Excelファイルを編集不可にする状態。全体ロック・個別ロックがある |
| adminユーザー | 全ユーザーの勤怠を閲覧・PDF出力・ロック管理できる管理者権限ユーザー |
| 一般ユーザー | 自分自身の勤怠のみ入力・閲覧できるユーザー |

## 3. 利用者・権限要件

### 3.1 ユーザー種別

| 種別 | 認証 | 主な操作 |
|---|---|---|
| admin | 1アカウントまたは複数可（要確認） | 全ユーザーの勤怠閲覧、Excel→PDF変換・出力、月次勤怠Excelの編集ロック（一括／個別）、ロック解除（個別） |
| 一般ユーザー | ユーザーごとに個別アカウント（氏名単位） | 自分の勤怠の入力、自分の勤怠の閲覧 |

> adminユーザーは自分自身の勤怠データを持たない。admin専用アカウントは管理業務のみを行い、勤怠入力の対象外とする。

### 3.2 権限マトリクス

| 機能 | 一般ユーザー | admin |
|---|---|---|
| 自分の勤怠入力 | ○（ロックされていない月のみ） | - |
| 自分の勤怠閲覧 | ○ | - |
| 他ユーザーの勤怠閲覧 | × | ○（全ユーザー） |
| Excel→PDF出力 | × | ○ |
| 月次一括ロック | × | ○ |
| ユーザー個別ロック | × | ○ |
| ユーザー個別ロック解除 | × | ○ |

## 4. 機能要件

### 4.1 認証・ログイン

- ユーザーはログインし、自分がadminか一般ユーザーかに応じた画面を表示する。
- 一般ユーザーは氏名（またはユーザーID）ごとに個別アカウントを持つ。

> **要確認事項**：認証方式（ID/パスワード、社内SSO、Microsoft 365連携など）。OneDriveを利用する前提のため、Microsoft 365アカウントでの認証（Azure AD/Entra ID連携）が有力候補。

### 4.2 月次Excelファイルの新規作成（テンプレートからの生成）

- 対象月・対象ユーザーを指定すると、テンプレート（原本シート）をコピーし、以下を自動設定してユーザー用の月次ファイルを生成する。

| セル | 内容 | 設定方法 |
|---|---|---|
| C8 | 対象月の初日（例：2026/06/01） | 対象月指定に応じてシステムが自動設定 |
| O5 | 社員番号 | ユーザーマスタから自動設定 |
| AH5 | 氏名 | ユーザーマスタから自動設定 |

- 生成されたファイルは、OneDrive上の該当月フォルダに、ユーザーごとのファイル名で保存する（既存の命名規則 `＿会社名＿勤務実績管理表_YYYYMM_氏名.xlsx` を踏襲）。
- 派遣先企業名は固定値（自社の企業名）として、全ユーザー・全月で同一の値を自動設定する。
- 派遣先部署名は現時点で運用が未確定のため、テンプレート生成時点では空欄（または任意入力可）とし、確定次第、自動設定するかユーザーマスタで保持するかを決定する。

> **要確認事項**：月次ファイルの新規作成は誰が・いつ・どのようにトリガーするか（毎月自動生成／adminが手動生成／ユーザー本人が初回アクセス時に生成、等）。派遣先部署名の管理方法（ユーザーマスタに保持／都度入力／未使用として廃止）。

### 4.3 勤怠入力（一般ユーザー）

フロント画面から、以下の項目を日ごとに入力できる。バックエンドは入力内容を対応するExcelファイルの該当セルへ反映する。

| 入力項目 | Excel上の位置 | 内容 |
|---|---|---|
| 休暇種類 | D14:D44（各日1行） | プルダウン選択：有休／午前半休／午後半休／長期連休／特別休暇／欠勤／振替休暇／休日出勤／振替出勤／稼働日／休日 |
| 出勤時間 | N列 | 時刻入力 |
| 退勤時間 | Q列 | 時刻入力 |
| 離業時間（私用外出・自社業務） | AC列 | 時間入力 |
| 自社工数内容 | AP列 | フリーテキスト |

- 入力対象期間はC8で指定された月の日数分（存在しない日付、例：2月30日等は非表示・入力不可）。
- 各行は「日」「曜日」に対応しており、曜日は自動算出（土日は法定休日として自動判定される想定、AY10/AY11の設定に基づく）。
- 実働時間・超過勤務・休日出勤時間・深夜時間等は、既存Excelの計算式に準拠し、システム側（またはExcel側）で自動集計する。

> **要確認事項**：休憩時間①②③など、既存Excelにあるが要求文に明記されていない項目をフロント入力対象に含めるか。今回の要件では「N列（出勤時間）」「Q列（退勤時間）」「AC列（離業時間）」「AP列（自社工数内容）」「D列（休暇種類）」を入力対象として明記されているため、休憩時間欄は含めない前提とするが、確認が必要。
>
> **⚠️リスク**：実際のサンプルファイルを解析したところ、休憩時間①②③欄（複数列）に日ごとに異なる時刻が入力されている記録があり、単純な固定値（マスタ欄の「所定7:30」等）ではなく、日々変動する運用の可能性がある。また、N列が「出勤時間」ではなく「始業時間」を指している可能性もあり、列の意味・入力対象範囲について依頼者に実運用を確認できていない。今回列挙した5項目だけでは、実際にユーザーが日々入力している項目を網羅できていない可能性がある。

### 4.4 勤怠閲覧

- 一般ユーザー：自分の月次勤怠を選択した月ごとに閲覧できる。
- adminユーザー：全ユーザー・全月の勤怠を閲覧できる（ユーザー・月を指定して検索／一覧表示）。

### 4.5 バリデーション（入力エラー表示）

既存Excelの条件付き書式で「問題のある入力」として色表示される以下のロジックを、フロントエンド入力時にも同様にエラーとして表示する。

| # | 条件（Excel条件付き書式ベース） | 内容 |
|---|---|---|
| 1 | 休暇種類（D列）＝土（AY10）または 日（AY11） | 曜日と休暇種類の指定が矛盾する等の入力（原本の条件をそのまま踏襲、詳細は既存ロジック要確認） |
| 2 | 休暇種類＝長期連休／特別休暇／欠勤／振替休暇 | 特定休暇種別選択時の表示ルール |
| 3 | 出勤時間または退勤時間が入力されているのに、休暇種類が「稼働日」等の勤務可能日区分でない | 非稼働日・休日として設定されている日に勤務時間が入力された場合にエラー |
| 4 | 出勤時間が入力されているが退勤時間が未入力（またはその逆） | 出退勤の片方のみ入力された場合にエラー |
| 5 | 非表示日（存在しない日付）に稼働時間が入力された場合 | 赤色で警告（変更履歴シートに記載の既存仕様） |
| 6 | 休日に稼働時間が入力された場合 | 赤色で警告（変更履歴シートに記載の既存仕様） |

- フロントエンドは、上記に該当する入力をリアルタイム、または保存時にエラーメッセージとして表示する。
- バックエンドでも同様のバリデーションを行い、Excel保存前に不正データを検出する（フロント・バック二重チェック）。

> **要確認事項**：条件付き書式のExcel数式（`$C14=$AY$10` 等）は原本ファイルの列構成に強く依存しているため、実装時に開発側で数式の詳細解析が必要。曖昧な条件（例：ルール1・2の業務的な意味）について、業務担当者への確認を推奨。

### 4.6 admin機能：Excel → PDF出力

- adminは、データベース（OneDrive）上の指定ユーザー・指定月のExcelファイルを選択し、PDFとして出力できる。
- 出力範囲：`原本`シートの `J1:AQ50` の範囲をPDF化する。用紙サイズはA4縦とする。
- 複数ユーザー分をまとめて出力できるようにする想定（例：対象月の全ユーザー、または選択した複数ユーザーを一括でPDF化）。ただし詳細仕様（1ファイルにまとめるか、ユーザーごとにファイルを分けて一括ダウンロードするか等）は未確定。

> **要確認事項**：複数ユーザー一括PDF出力時の出力形式（1つのPDFに全員分を結合するか、ユーザーごとに個別PDFをZIP等でまとめるか）。

### 4.7 admin機能：編集ロック管理

- 指定した月の勤怠Excelファイルに対し、以下の操作ができる。

| 操作 | 内容 |
|---|---|
| まとめてロック | 指定月の全ユーザーファイルを一括で編集不可にする |
| 個別にロック | 指定月・指定ユーザーのファイルのみ編集不可にする |
| 個別に解除 | ロック済みの指定月・指定ユーザーのファイルを編集可能に戻す |

- ロック状態は、一般ユーザーの入力画面に反映され、ロック中は入力操作を無効化（またはエラー表示）する。
- ロック状態は、Excelファイル自体の保護機能（シート保護等）は使用せず、別途ロック状態管理用のデータストア（例：DB、JSON、管理用テーブル等）で「月×ユーザー」単位のロック状態を保持する。

> **要確認事項**：ロック状態管理用データストアの実装方式（DB／JSONファイル／その他）。まとめてロックの解除（一括解除）機能の要否。

## 5. データ要件

### 5.1 データストア構成

- OneDrive上のフォルダ構成：月ごとのフォルダ（`YYYYMM`形式）の下に、ユーザーごとのExcelファイルを格納する。
- ファイル命名規則：`【会社名】勤務実績管理表_YYYYMM_氏名.xlsx`（会社名は固定値）

```
OneDrive指定のディレクトリ/
  ├─ 202606/
  │   ├─ 【会社名】勤務実績管理表_202606_ユーザー1の氏名.xlsx
  │   ├─ 【会社名】勤務実績管理表_202606_ユーザー2の氏名.xlsx
  │   └─ ...
  ├─ 202607/
  │   ├─ 【会社名】勤務実績管理表_202607_ユーザー1の氏名.xlsx
  │   ├─ 【会社名】勤務実績管理表_202607_ユーザー2の氏名.xlsx
  │   └─ ...
```

- PDF出力ファイルも同様に月フォルダ配下に保存する想定（保存場所は要確認）。ファイル名はExcelと対になる形とする：`【会社名】勤務実績管理表_YYYYMM_氏名.pdf`

> **要確認事項**：PDFファイルの保存先（Excelと同じ月フォルダ内か、専用のPDF出力フォルダを別途設けるか）。PDFはOneDriveに保存せず、都度ブラウザでダウンロードのみとする運用も選択肢としてありうる。

### 5.2 OneDriveアクセス

- 保存先は社内のOneDrive（法人テナント）を使用する。バックエンドはOneDriveのファイルをMicrosoft Graph API等を通じて読み書きする想定。
- サインイン方式は未確定。以下の2方式が考えられ、どちらを採用するかで実装・運用が大きく変わる。

| 方式 | 概要 | ユーザー側のOneDriveサインイン |
|---|---|---|
| A. サービスアカウント方式（アプリケーション権限） | システム専用の1つのOneDriveアカウント（サービスアカウント）にアプリ登録し、バックエンドが常にそのアカウントとして全ファイルを読み書きする | 不要。一般ユーザー・adminはシステム独自の認証（またはSSO）でログインするのみで、OneDriveへの個別サインインは発生しない |
| B. 委任アクセス方式（ユーザー権限） | 各ユーザーが自身のMicrosoft 365アカウントでサインインし、そのユーザー権限でOneDriveにアクセスする | 必要。ユーザーは初回アクセス時等にMicrosoft 365アカウントでのサインイン（OAuth認証）が必要になる |

- 案Aであれば、一般ユーザーはOneDriveの存在を意識せず、システムの画面上で入力・閲覧が完結する。案Bであれば、Microsoft 365アカウントとの連携が前提となり、認証フローが複雑になる代わりに、OneDrive側のアクセス権限管理と連動できる。

> **要確認事項**：どちらの方式を採用するか（社内のMicrosoft 365テナント管理者に、サービスアカウントの作成・アプリ登録の許可が得られるかによる）。委任アクセス方式の場合、ユーザーごとのOneDriveアクセス権限（フォルダの共有設定）を事前に整備する必要がある。

### 5.3 閲覧権限とプレビュー

- 保存された勤怠Excelデータは、全ユーザー（admin・一般ユーザー問わず）が閲覧可能という前提（OneDrive上のファイル自体には全員の閲覧権限がある）。
- ただし、本システムの権限要件（3.2節）では「一般ユーザーは自分の勤怠のみ閲覧可」としているため、**OneDriveファイル自体への直接アクセス権限とは別に、システム（アプリケーション）側でアクセス制御を行う**必要がある。
  - システムの画面経由でアクセスする限りは、一般ユーザーは自分のデータのみが表示され、他ユーザーのデータはAPIレベルで遮断される。
  - 一方、OneDrive上のファイルに全員が閲覧権限を持つ場合、ユーザーがOneDriveを直接開けば他ユーザーのExcelファイルも閲覧できてしまう可能性がある。この点はシステムの権限制御では防げない。
- 勤怠データのプレビュー方法（画面上での表示）は、Excelファイルをブラウザ上で直接開くのではなく、バックエンドがExcelの内容を読み取り、Webの表形式UI（HTMLテーブル）として整形して表示する方式とする。Excelそのものをブラウザ内蔵ビューア等で開く方式は取らない。

> **要確認事項**：OneDrive上のファイルに全員が閲覧権限を持つことについて、意図的な運用か（全員が全員の勤怠を見られてよい）、それともシステム経由のアクセス制御のみで十分とするか、OneDriveのフォルダ権限自体をユーザーごとに制限すべきかを確認したい。

### 5.3 ユーザーマスタ

- 社員番号・氏名・アカウント情報（ログインID等）・権限区分（admin／一般）を管理するマスタが別途必要。

> **要確認事項**：ユーザーマスタの管理方法（別Excel／DB／OneDrive上のJSON等）、管理者による追加・編集機能の要否。

## 6. 非機能要件（案）

| 項目 | 内容 |
|---|---|
| 可用性 | 社内利用を想定、営業時間内の利用を基本とする（要確認） |
| セキュリティ | OneDriveアクセスの認証情報を安全に管理。ユーザーごとのアクセス権限を適切に分離 |

## 7. 画面要件

### 7.1 画面一覧

| 画面 | 対象ユーザー | 内容 |
|---|---|---|
| ログイン画面 | 全員 | 認証 |
| 勤怠入力画面 | 一般ユーザー | 月選択→日別の休暇種類・出退勤時間・離業時間・自社工数内容を入力。バリデーションエラーを表示 |
| 勤怠閲覧画面（自分用） | 一般ユーザー | 月選択→自分の入力内容を一覧表示（プレビュー） |
| 勤怠閲覧画面（全ユーザー） | admin | ユーザー・月を指定して閲覧（プレビュー） |
| PDF出力画面 | admin | ユーザー・月を指定してPDF生成・ダウンロード |
| ロック管理画面 | admin | 月を指定して、まとめてロック／ユーザーごとの個別ロック・解除を操作 |

### 7.2 画面遷移

```
[ログイン]
    │
    ├─ 一般ユーザー ─▶ [勤怠入力／閲覧画面]（自分の月次データのみ）
    │
    └─ admin ────────▶ [管理トップ]
                            ├─▶ [勤怠閲覧画面（全ユーザー）]
                            ├─▶ [PDF出力画面]
                            └─▶ [ロック管理画面]
```

### 7.3 勤怠入力画面（一般ユーザー）詳細

**構成要素**

| 要素 | 内容 |
|---|---|
| ヘッダー | 対象年月の表示・切り替え（前月／翌月、または月選択プルダウン）、氏名・社員番号の表示、ロック状態の表示 |
| 入力テーブル | 1日1行。列：日付／曜日／休暇種類（プルダウン）／出勤時間／退勤時間／離業時間／自社工数内容 |
| バリデーション表示 | 入力内容に問題がある行はセル・行を強調表示し、エラーメッセージを表示 |
| 保存ボタン | 入力内容をまとめて保存（バックエンド経由でExcelへ反映） |
| ロック中の表示 | ロックされている月は入力欄をすべて無効化し、「この月はロックされています」等のメッセージを表示 |

**休暇種類による入力欄の制御**

- 「稼働日」「休日出勤」「振替出勤」等、勤務が発生する区分を選択した場合のみ、出勤時間・退勤時間・離業時間の入力欄を有効化する。
- 「有休」「長期連休」「特別休暇」「欠勤」「休日」等、勤務が発生しない区分を選択した場合は、該当欄を自動的に無効化（グレーアウト）する。
- 「午前半休」「午後半休」の場合は、半日分の勤務時間のみ入力可能とする（詳細な制御ルールは要確認）。

**バリデーションエラーの表示例**

- 休日区分の日に出勤・退勤時間が入力されている → 該当行を警告色で表示し、「休日ですが稼働時間が入力されています」等のメッセージを表示
- 出勤時間のみ入力されて退勤時間が未入力 → 該当セルを警告色で表示

### 7.4 勤怠閲覧画面（プレビュー）

- 保存済みのExcelファイルの内容を、バックエンドが読み取り、Web上のテーブル形式（HTMLテーブル）で整形して表示する。Excelファイルをブラウザで直接開く方式は取らない。
- 一般ユーザーは自分の月次データのみ選択・閲覧可能。
- adminはユーザー選択欄・月選択欄から任意の組み合わせを選び閲覧可能。
- 閲覧画面は入力画面と同様のテーブルレイアウトを使うが、入力欄はすべて読み取り専用（編集不可）とする。

### 7.5 PDF出力画面（admin）

- ユーザーを1名または複数名選択し、対象月を指定してPDFを生成する。
- 出力範囲：`J1:AQ50`、A4縦。
- 生成後、ブラウザ上でダウンロード（またはOneDriveへの保存、要確認）。

### 7.6 ロック管理画面（admin）

- 対象月を選択すると、その月の全ユーザーのロック状態一覧（ユーザー名・ロック中／編集可能）が表示される。
- 「まとめてロック」ボタンで一括ロック。
- 各ユーザー行に「ロック」「解除」の個別操作ボタンを配置。

## 9. 処理フロー（勤怠入力の例）

1. 一般ユーザーがログインする。
2. 対象月を選択する。
3. バックエンドが該当ユーザー・該当月のExcelファイルをOneDriveから取得する（存在しなければテンプレートから新規作成）。
4. ロック状態を確認し、ロック中であれば入力不可として表示する。
5. ユーザーが休暇種類・出勤時間・退勤時間・離業時間・自社工数内容を入力する。
6. フロントエンドおよびバックエンドでバリデーションを実施し、問題があればエラー表示する。
7. 保存操作により、バックエンドがExcelファイルの該当セルを更新し、OneDriveへ書き戻す。

---

## 10. PDF出力フロー（admin）

1. adminがログインする。
2. 対象ユーザー・対象月を選択する。
3. バックエンドがOneDriveから該当Excelファイルを取得する。
4. Excel→PDF変換処理を行う。
5. PDFをダウンロード（またはブラウザ表示）する。

---

## 11. ロック管理フロー（admin）

1. adminがログインする。
2. 対象月を選択する。
3. 「まとめてロック」を選択した場合：該当月の全ユーザーファイルをロック状態にする。
4. 「個別にロック」を選択した場合：ユーザーを指定してロック状態にする。
5. 「個別に解除」を選択した場合：ロック済みユーザーを指定して解除する。
6. ロック状態は各ユーザーの入力画面に即時反映される。

## 14. 開発・技術方式に関する参考比較

| 観点 | Streamlit（Python） | HTML/JS + Python API |
|---|---|---|
| 開発速度 | 速い（フォーム部品が豊富） | フロント・バック分離で工数はやや大きい |
| UIの自由度 | 限定的（Streamlitの標準コンポーネント中心） | 高い（自由にデザイン可能） |
| Excel/OneDrive連携 | Pythonバックエンド内で完結しやすい | API経由でPython側に集約 |
| 保守性 | 単一アプリで完結し保守しやすい | 責務分離により大規模化に対応しやすい |
| 想定利用規模 | 小〜中規模の社内ツールに適する | 中〜大規模、将来的な拡張を見込む場合に適する |

現時点の要求（社内向け勤怠管理、ユーザー数は限定的と推測）を踏まえると、開発速度・保守性の観点でStreamlit案が有力だが、最終的な採用方式は「13. 未確定事項」の確認後に決定する。
