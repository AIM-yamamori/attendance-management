## 1. 概要

### 1.1 目的

現在Excelファイル（勤務実績管理表）を個人ごと・月ごとに作成し、OneDrive上で管理している勤怠管理業務を、Webシステム化する。ユーザーはブラウザから勤怠を入力・閲覧でき、管理者（admin）は全ユーザーの勤怠を閲覧・PDF出力・編集ロック管理できるようにする。

### 1.2 対象システムの範囲

- フロントエンド：ブラウザで動作するWebアプリケーション
- バックエンド：勤怠データの保存・検証・PDF出力・ロック制御を担うAPI/サーバー
- データストア：OneDrive上のExcelファイル群（ユーザー×月ごとのファイル）を実データベースとして利用

### 1.3 想定技術構成（案）

| 方式 | 内容 |
|---|---|
| 案A | Streamlit（Python）で一体型Webアプリを構築。フロント・バック分離ではなく単一Pythonアプリ内で完結 |
| 案B | HTML/JS（フロントエンド）＋ Python API（バックエンド、例：FastAPI/Flask）の分離構成 |

どちらの案を採用するかは非機能要件・開発体制次第。本書では両案に対応できるよう、機能要件はUIとロジックを分離して記述する。

> **要確認事項**：Streamlit案・分離構成案のどちらを採用するか、後述の「14. 未確定事項・要確認事項」にまとめて記載。

## 2. 用語定義

| 用語 | 説明 |
|---|---|
| 勤務実績管理表 | 1ユーザー・1ヶ月分の勤怠を記録するExcelファイル（アップロードされたサンプルが原本） |
| テンプレート | 新規月次ファイルを生成する際の元となるExcelファイル（`原本`シートを使用） |
| ロック | 対象月の勤怠Excelファイルを編集不可にする状態。全体ロック・個別ロックがある |
| adminユーザー | 全ユーザーの勤怠を閲覧・PDF出力・ロック管理できる管理者権限ユーザー |
| 一般ユーザー | 自分自身の勤怠のみ入力・閲覧できるユーザー |

## 3. 利用者・権限要件

### 3.1 ユーザー種別

| 種別 | 認証 | 主な操作 |
|---|---|---|
| admin | 1アカウントまたは複数可（要確認） | 全ユーザーの勤怠閲覧、Excel→PDF変換・出力、月次勤怠Excelの編集ロック（一括／個別）、ロック解除（個別） |
| 一般ユーザー | ユーザーごとに個別アカウント（氏名単位） | 自分の勤怠の入力、自分の勤怠の閲覧 |

> adminユーザーは自分自身の勤怠データを持たない。admin専用アカウントは管理業務のみを行い、勤怠入力の対象外とする。

### 3.2 権限マトリクス

| 機能 | 一般ユーザー | admin |
|---|---|---|
| 自分の勤怠入力 | ○（ロックされていない月のみ） | - |
| 自分の勤怠閲覧 | ○ | - |
| 他ユーザーの勤怠閲覧 | × | ○（全ユーザー） |
| Excel→PDF出力 | × | ○ |
| 月次一括ロック | × | ○ |
| ユーザー個別ロック | × | ○ |
| ユーザー個別ロック解除 | × | ○ |

## 4. 機能要件

### 4.1 認証・ログイン

- ユーザーはログインし、自分がadminか一般ユーザーかに応じた画面を表示する。
- 一般ユーザーは氏名（またはユーザーID）ごとに個別アカウントを持つ。

> **要確認事項**：認証方式（ID/パスワード、社内SSO、Microsoft 365連携など）。OneDriveを利用する前提のため、Microsoft 365アカウントでの認証（Azure AD/Entra ID連携）が有力候補。

### 4.2 月次Excelファイルの新規作成（テンプレートからの生成）

- 対象月・対象ユーザーを指定すると、テンプレート（原本シート）をコピーし、以下を自動設定してユーザー用の月次ファイルを生成する。

| セル | 内容 | 設定方法 |
|---|---|---|
| C8 | 対象月の初日（例：2026/06/01） | 対象月指定に応じてシステムが自動設定 |
| O5 | 社員番号 | ユーザーマスタから自動設定 |
| AH5 | 氏名 | ユーザーマスタから自動設定 |

- 生成されたファイルは、OneDrive上の該当月フォルダに、ユーザーごとのファイル名で保存する（既存の命名規則 `＿会社名＿勤務実績管理表_YYYYMM_氏名.xlsx` を踏襲）。
- 派遣先企業名は固定値（自社の企業名）として、全ユーザー・全月で同一の値を自動設定する。
- 派遣先部署名は現時点で運用が未確定のため、テンプレート生成時点では空欄（または任意入力可）とし、確定次第、自動設定するかユーザーマスタで保持するかを決定する。

> **要確認事項**：月次ファイルの新規作成は誰が・いつ・どのようにトリガーするか（毎月自動生成／adminが手動生成／ユーザー本人が初回アクセス時に生成、等）。派遣先部署名の管理方法（ユーザーマスタに保持／都度入力／未使用として廃止）。

### 4.3 勤怠入力（一般ユーザー）

フロント画面から、以下の項目を日ごとに入力できる。バックエンドは入力内容を対応するExcelファイルの該当セルへ反映する。

| 入力項目 | Excel上の位置 | 内容 |
|---|---|---|
| 休暇種類 | D14:D44（各日1行） | プルダウン選択：有休／午前半休／午後半休／長期連休／特別休暇／欠勤／振替休暇／休日出勤／振替出勤／稼働日／休日 |
| 出勤時間 | N列 | 時刻入力 |
| 退勤時間 | Q列 | 時刻入力 |
| 離業時間（私用外出・自社業務） | AC列 | 時間入力 |
| 自社工数内容 | AP列 | フリーテキスト |

- 入力対象期間はC8で指定された月の日数分（存在しない日付、例：2月30日等は非表示・入力不可）。
- 各行は「日」「曜日」に対応しており、曜日は自動算出（土日は法定休日として自動判定される想定、AY10/AY11の設定に基づく）。
- 実働時間・超過勤務・休日出勤時間・深夜時間等は、既存Excelの計算式に準拠し、システム側（またはExcel側）で自動集計する。

> **要確認事項**：休憩時間①②③（既存Excelに存在する項目）、始業/終業時間の内訳等、アップロードされたサンプルに存在するが要求文に明記されていない項目を、フロント入力対象に含めるか。今回の要件では「N列（出勤時間）」「Q列（退勤時間）」「AC列（離業時間）」「AP列（自社工数内容）」「D列（休暇種類）」を入力対象として明記されているため、休憩時間欄は含めない前提とするが、確認が必要。

### 4.4 勤怠閲覧

- 一般ユーザー：自分の月次勤怠を選択した月ごとに閲覧できる。
- adminユーザー：全ユーザー・全月の勤怠を閲覧できる（ユーザー・月を指定して検索／一覧表示）。

### 4.5 バリデーション（入力エラー表示）

既存Excelの条件付き書式で「問題のある入力」として色表示される以下のロジックを、フロントエンド入力時にも同様にエラーとして表示する。

| # | 条件（Excel条件付き書式ベース） | 内容 |
|---|---|---|
| 1 | 休暇種類（D列）＝土（AY10）または 日（AY11） | 曜日と休暇種類の指定が矛盾する等の入力（原本の条件をそのまま踏襲、詳細は既存ロジック要確認） |
| 2 | 休暇種類＝長期連休／特別休暇／欠勤／振替休暇 | 特定休暇種別選択時の表示ルール |
| 3 | 出勤時間または退勤時間が入力されているのに、休暇種類が「稼働日」等の勤務可能日区分でない | 非稼働日・休日として設定されている日に勤務時間が入力された場合にエラー |
| 4 | 出勤時間が入力されているが退勤時間が未入力（またはその逆） | 出退勤の片方のみ入力された場合にエラー |
| 5 | 非表示日（存在しない日付）に稼働時間が入力された場合 | 赤色で警告（変更履歴シートに記載の既存仕様） |
| 6 | 休日に稼働時間が入力された場合 | 赤色で警告（変更履歴シートに記載の既存仕様） |

- フロントエンドは、上記に該当する入力をリアルタイム、または保存時にエラーメッセージとして表示する。
- バックエンドでも同様のバリデーションを行い、Excel保存前に不正データを検出する（フロント・バック二重チェック）。

> **要確認事項**：条件付き書式のExcel数式（`$C14=$AY$10` 等）は原本ファイルの列構成に強く依存しているため、実装時に開発側で数式の詳細解析が必要。曖昧な条件（例：ルール1・2の業務的な意味）について、業務担当者への確認を推奨。

### 4.6 admin機能：Excel → PDF出力

- adminは、データベース（OneDrive）上の指定ユーザー・指定月のExcelファイルを選択し、PDFとして出力できる。
- 出力範囲：`原本`シートの `J1:AQ50` の範囲をPDF化する。
- 複数ユーザー分をまとめて出力できるようにする想定（例：対象月の全ユーザー、または選択した複数ユーザーを一括でPDF化）。ただし詳細仕様（1ファイルにまとめるか、ユーザーごとにファイルを分けて一括ダウンロードするか等）は未確定。

> **要確認事項**：複数ユーザー一括PDF出力時の出力形式（1つのPDFに全員分を結合するか、ユーザーごとに個別PDFをZIP等でまとめるか）。

### 4.7 admin機能：編集ロック管理

- 指定した月の勤怠Excelファイルに対し、以下の操作ができる。

| 操作 | 内容 |
|---|---|
| まとめてロック | 指定月の全ユーザーファイルを一括で編集不可にする |
| 個別にロック | 指定月・指定ユーザーのファイルのみ編集不可にする |
| 個別に解除 | ロック済みの指定月・指定ユーザーのファイルを編集可能に戻す |

- ロック状態は、一般ユーザーの入力画面に反映され、ロック中は入力操作を無効化（またはエラー表示）する。
- ロック状態は、Excelファイル自体の保護機能（シート保護等）は使用せず、別途ロック状態管理用のデータストア（例：DB、JSON、管理用テーブル等）で「月×ユーザー」単位のロック状態を保持する。

> **要確認事項**：ロック状態管理用データストアの実装方式（DB／JSONファイル／その他）。まとめてロックの解除（一括解除）機能の要否。

## 5. データ要件

### 5.1 データストア構成

- OneDrive上のフォルダ構成：月ごとのフォルダの下に、ユーザーごとのExcelファイルを格納する。

```
/勤怠管理/
  ├─ 2026年06月/
  │   ├─ ＿会社名＿勤務実績管理表_202606_氏名A.xlsx
  │   ├─ ＿会社名＿勤務実績管理表_202606_氏名B.xlsx
  │   └─ ...
  ├─ 2026年07月/
  │   └─ ...
```

### 5.2 OneDriveアクセス

- バックエンドはOneDriveのファイルをMicrosoft Graph API等を通じて読み書きする想定。

> **要確認事項**：OneDriveへの認証方式（アプリ登録・クライアントID/シークレット、委任アクセスかアプリケーションアクセスか）。OneDrive for Business（法人テナント）かパーソナルOneDriveか。

### 5.3 ユーザーマスタ

- 社員番号・氏名・アカウント情報（ログインID等）・権限区分（admin／一般）を管理するマスタが別途必要。

> **要確認事項**：ユーザーマスタの管理方法（別Excel／DB／OneDrive上のJSON等）、管理者による追加・編集機能の要否。

## 9. 処理フロー（勤怠入力の例）

1. 一般ユーザーがログインする。
2. 対象月を選択する。
3. バックエンドが該当ユーザー・該当月のExcelファイルをOneDriveから取得する（存在しなければテンプレートから新規作成）。
4. ロック状態を確認し、ロック中であれば入力不可として表示する。
5. ユーザーが休暇種類・出勤時間・退勤時間・離業時間・自社工数内容を入力する。
6. フロントエンドおよびバックエンドでバリデーションを実施し、問題があればエラー表示する。
7. 保存操作により、バックエンドがExcelファイルの該当セルを更新し、OneDriveへ書き戻す。

---

## 10. PDF出力フロー（admin）

1. adminがログインする。
2. 対象ユーザー・対象月を選択する。
3. バックエンドがOneDriveから該当Excelファイルを取得する。
4. Excel→PDF変換処理を行う。
5. PDFをダウンロード（またはブラウザ表示）する。

---

## 11. ロック管理フロー（admin）

1. adminがログインする。
2. 対象月を選択する。
3. 「まとめてロック」を選択した場合：該当月の全ユーザーファイルをロック状態にする。
4. 「個別にロック」を選択した場合：ユーザーを指定してロック状態にする。
5. 「個別に解除」を選択した場合：ロック済みユーザーを指定して解除する。
6. ロック状態は各ユーザーの入力画面に即時反映される。

## 12. 既存Excelファイルの仕様調査結果（参考情報）

アップロードされたサンプルファイル `_会社名_勤務実績管理表_202606_氏名.xlsx` を調査した結果、以下を確認した。

- シート構成：`原本`（実データ入力シート）、`変更履歴`、`記入例`（保護済み・入力例シート）
- 主要セル
  - `C8`：対象月初日
  - `O5`：社員番号
  - `AH5`：氏名
  - `D14:D44`：休暇種類（入力規則：リスト選択、参照範囲 `AY14:AY24`）
  - `N`列：出勤時間、`Q`列：退勤時間、`AC`列：離業時間、`AP`列：自社工数内容
- 休暇種類リスト（`AY14:AY24`）：有休／午前半休／午後半休／長期連休／特別休暇／欠勤／振替休暇／休日出勤／振替出勤／稼働日／休日
- 条件付き書式：D14:D44・N9:S39・K9:AP39 等の範囲に対し、曜日区分（土＝AY10／日＝AY11）や休暇種別との組み合わせによる複数の警告ルールが設定されている（該当時にセルが赤色等で塗りつぶされる）。
- `原本`シートはシート保護がかかっていない（`protection=False`）一方、`記入例`シートは保護されている（`protection=True`）。実運用のテンプレートでは保護設定を要確認。

## 14. 開発・技術方式に関する参考比較

| 観点 | Streamlit（Python） | HTML/JS + Python API |
|---|---|---|
| 開発速度 | 速い（フォーム部品が豊富） | フロント・バック分離で工数はやや大きい |
| UIの自由度 | 限定的（Streamlitの標準コンポーネント中心） | 高い（自由にデザイン可能） |
| Excel/OneDrive連携 | Pythonバックエンド内で完結しやすい | API経由でPython側に集約 |
| 保守性 | 単一アプリで完結し保守しやすい | 責務分離により大規模化に対応しやすい |
| 想定利用規模 | 小〜中規模の社内ツールに適する | 中〜大規模、将来的な拡張を見込む場合に適する |

現時点の要求（社内向け勤怠管理、ユーザー数は限定的と推測）を踏まえると、開発速度・保守性の観点でStreamlit案が有力だが、最終的な採用方式は「13. 未確定事項」の確認後に決定する。

## 15. 質問事項

本書を作成・システムを設計するにあたり、以下について依頼者に確認したい。

### 技術方式
1. フロントエンド・バックエンドは「Streamlit（Python）一体型」「HTML/JS＋Python API分離型」のどちらを希望するか。
2. サーバーの設置場所（社内オンプレ／クラウド／既存の社内システム基盤があるか）。
3. 想定する同時利用者数・利用時間帯（社内のみの営業時間内利用で問題ないか）。

### 認証・ユーザー管理
4. ログイン認証は何を使うか（Microsoft 365/Azure ADとの連携、独自ID・パスワード発行、その他）。
5. ユーザーマスタ（氏名・社員番号・権限区分）は誰がどこで管理するか（新規追加・退職者削除等の運用フローを含む）。
6. adminアカウントは何人・誰が持つか。

### Excel／OneDrive連携
7. 利用しているOneDriveは法人テナント（OneDrive for Business）か、個人アカウントか。
8. OneDriveへのAPIアクセス（Microsoft Graph API等）のアプリ登録は依頼者側で用意できるか、それとも別途申請が必要か。
9. 派遣先部署名は今後どのように扱うか（廃止する／ユーザーごとに固定値を持たせる／都度入力可能にする）。
10. 派遣先企業名は今回「固定」とのことだが、具体的な企業名・表記（正式名称）を教えてほしい。

### 入力・バリデーション
11. 休憩時間①②③、始業・終業時間の内訳など、既存Excelにあるが今回の要求文に明記されていない項目は、システムでは入力不要として問題ないか。
12. 条件付き書式に基づくバリデーションルール（曜日と休暇種別の組み合わせ、休日への稼働時間入力など）について、業務的にどのような意図のルールか詳細を確認したい（実装のため数式の意味を正確に把握する必要がある）。
13. 休暇申請に上長承認等のワークフローは不要という理解でよいか（今回は「入力と閲覧」のみと認識）。

### PDF出力
14. 複数ユーザー分をまとめて出力する場合、1つのPDFに全員分を結合してほしいか、ユーザーごとに個別PDFを生成してZIP等でまとめてダウンロードしたいか。
15. PDF出力の実行頻度・想定利用シーン（月次締め処理時のみ／随時、等）。

### ロック管理
16. ロック状態を管理する仕組みについて、DBやJSONファイルなど実装方式に希望はあるか。
17. 「まとめてロック」した月を一括で解除する機能は必要か、それとも解除は必ず個別に行う運用でよいか。

### 運用・保守
18. 社外（自宅等）からのアクセスを許可する必要があるか。
19. 操作履歴（誰がいつ何を編集したか）を記録する監査ログ機能は必要か。
20. 本システム稼働後、既存のExcelテンプレート（原本・記入例・変更履歴シート）の運用（手動配布等）は完全に廃止してよいか。
