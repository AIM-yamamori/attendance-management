# Streamlitアプリのデプロイ方法について（費用最優先）

## エグゼクティブ・サマリー（結論）

**第一推奨：案B「VPS + Cloudflare（無料枠）」**
月額600〜1,300円程度でSQLiteの永続化に不安がなく、Cloudflareの無料プランでCDN・WAF・SSLも追加費用ゼロで得られる。Streamlitの状態保持（後述）とも相性が良く、費用・安定性・運用のバランスが最も良い。

**次点候補：**
- 運用の手間を極力減らしたい → **案C「Fly.io」**（無料枠あり・東京リージョン対応）
- GCPのエコシステムに寄せたい、コストを極限まで下げたい → **案G「Google Cloud Run + Litestream」**（費用は最安クラスだが構築難易度がやや高い）

**見送り推奨：**
- 案E「Render」：無料プランではSQLite永続化不可、有料プラン前提で費用面の優位性が薄い
- 案F「Cloudflare Containers」：SQLite永続化の標準手段がなく、リスク・工数に見合わない

---

## 前提条件・選定基準

以下の3軸を優先順位順に評価基準とする。

1. **費用最優先**（月額固定費・従量費の両方を最小化）
2. **SQLiteの安全な永続化**（データが消えない・壊れない構成であること）
3. **運用保守の手間**（人的コスト・スキル要求水準）

Cloudflareの利用は必須条件ではなく、上記基準を満たせるなら他の方法も対等に比較する。

### 現状の構成（変更なし）

- **Streamlit**（Python製Webアプリ）
- **Docker**でコンテナ化
- **SQLite**（ファイルベースのDB。外部DBサーバー不要）
- **.env**（環境変数ファイルで設定値・秘密情報を管理）
- **LibreOffice**（ドキュメント変換処理）

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
    libreoffice-calc \
    libreoffice-core \
    fonts-noto-cjk \
    locales \
    && localedef -i ja_JP -c -f UTF-8 -A /usr/share/locale/locale.alias ja_JP.UTF-8 \
    && rm -rf /var/lib/apt/lists/*
```

**SQLiteはファイル1つで完結するDBのため、外部のマネージドDBサービス（Cloud SQL等）が不要**。これにより「コンテナ＋永続ディスク1つ」があれば構成が完結し、選択肢がシンプルになる。ただし、永続ディスクを持てない環境（再起動のたびに初期化される環境）ではデータが消える点に注意が必要。

## 技術的な補足事項（全案共通で影響する制約）

### Streamlitの状態保持について
StreamlitはWebSocketで画面とつながり続け、操作中の状態（Session State）をサーバー側で保持する設計になっている。**オートスケールでインスタンスが複数に増減する環境や、スリープ（コールドスタート）が発生する環境では、操作中にセッションが切断されたり画面の状態がリセットされる可能性がある。** この点はSQLiteの永続化問題と根っこが同じで、「インスタンスを1つに固定できる環境（VPSや、インスタンス数1固定のCloud Run）」の方が安定する。

### LibreOfficeのメモリ要件について
LibreOfficeはドキュメント変換の瞬間、**512MB〜1GB以上のメモリを一時的に消費する**ことがある。Fly.io・Railway・Renderなどの最小プラン（メモリ512MB程度）で動かす場合、変換処理のタイミングで**OOM（メモリ不足）によるコンテナ強制終了**が起きるリスクがある。これらのサービスを検討する場合は、最小プランではなく1段階上のメモリプランを選ぶことを推奨する。

### SQLiteのバックアップ運用について
- **VPS（案A・B）:** 永続化自体の不安はないが、ディスク障害・誤操作に備えて`cron`等でSQLiteファイルを定期的に別の場所へバックアップする運用を自分たちで組む必要がある
- **Cloud Run + Litestream（案G）:** 変更が発生するたびに自動でGCSへレプリケートされるため、**バックアップの仕組みが標準で組み込まれる**。この点は案Gの数少ない明確な長所

## 案B: VPS + Cloudflare（無料枠のみ使用）【第一推奨】

案Aと基本構成は同じだが、ドメイン・CDN・WAF・SSLの部分だけCloudflareの**無料プラン**を使う構成。Cloudflare Tunnelを使えばVPS側のポートを一切外部公開せずに済む。

### できること・担当範囲
- **VPSの担当:** アプリ実行（Streamlit＋LibreOffice）、SQLiteファイルの永続化、.envの管理
- **Cloudflareの担当（無料）:** ドメイン・DNS、CDN、WAF/DDoS対策、SSL証明書、Tunnel経由の通信経路

### メリット
- 案Aの費用感をほぼ維持したまま、**無料でCDN・WAF・自動SSLが手に入る**
- Cloudflare Tunnelを使うとVPS側で80/443番ポートを外部に開ける必要がなくなり、セキュリティが向上
- SQLiteの永続化・Streamlitの状態保持ともにインスタンスが1つに固定されるため不安がない

### デメリット
- Cloudflareの管理画面・Tunnel設定という学習コストが案Aに追加される
- Tunnelの常時起動（`cloudflared`のサービス化）を忘れると接続が切れる
- OSの保守・SQLiteのバックアップ運用（cron等）は自社対応が必要

### 費用目安
- VPS：月額500〜1,200円程度（さくらのVPS、ConoHa VPS等の最安〜中位プラン）
- ドメイン：年間1,000〜2,000円程度（.comの場合）
- Cloudflare：**無料**
- **合計：月換算で約600〜1,300円程度**

### 運用開始までの工数
半日〜1日程度（VPS初期設定2〜3時間＋Docker構築2〜3時間＋Cloudflare Tunnel設定1時間）

### 難易度
**中。** Linuxサーバーの基本操作（SSH、Docker、Nginx）に加え、`cloudflared`のセットアップが必要。公式手順に従えば大きな障壁はない。

### デプロイ手順
1. VPS（さくらのVPS、ConoHa VPS等）を契約し、Ubuntu等でサーバーを立てる
2. `apt update && apt install docker.io docker-compose` でDocker環境を構築
3. 既存のDockerfileと`docker-compose.yml`をサーバーに配置（SQLiteファイルの保存先はホスト側ディレクトリにボリュームマウントし、永続化する）
4. `.env`ファイルをサーバー上に直接配置（Gitには含めず、SCP等で安全に転送）
5. `docker compose up -d`でコンテナを起動
6. Cloudflareに無料アカウントを作成し、ドメインをネームサーバーごとCloudflareに移管（またはCNAME委任）
7. VPSに`cloudflared`をインストールし、`cloudflared tunnel login`でアカウント連携
8. `cloudflared tunnel create <トンネル名>`でトンネルを作成し、`config.yml`でStreamlitのポート（8501）へのルーティングを設定
9. Cloudflareダッシュボードでトンネルに対応するDNSレコード（CNAME）を追加
10. `cloudflared`をsystemdサービス化し、サーバー再起動時も自動起動するよう設定
11. Cloudflare側でSSL/TLSモードを「Full」に設定し、動作確認
12. SQLiteファイルの定期バックアップ用cronジョブを設定（別ディレクトリまたは外部ストレージへコピー）

## 案C: Fly.io【次点候補：運用の手間を減らしたい場合】

Dockerfileをそのままデプロイできるサービス。永続ディスク（Volumes）を持てるため、SQLiteとの相性が良い。

### できること・担当範囲
Fly.ioが**ドメイン以外のほぼすべて**（アプリ実行、SQLite永続化用のVolume、.envに相当するSecrets管理）を担う。

### メリット
- Dockerfileがそのまま使える。既存構成の変更がほぼ不要
- **Volumes機能で永続ディスクを持てるため、SQLiteファイルの永続化に対応**
- 無料枠があり、小規模な使用なら無料〜数百円で収まる可能性がある
- 東京リージョンに対応しており、日本からのアクセスでも速度面で有利
- インスタンス数を1に保てば、Streamlitの状態保持の問題も起きにくい

### デメリット
- 完全従量課金のため、アクセスが増えると費用が読みにくくなる
- 過去に大規模障害の実績があり、安定性はVPSほど盤石ではないという評価もある
- **最小構成のメモリプランではLibreOfficeの変換処理でOOM（メモリ不足）が起きるリスクがあるため、1段階上のプランを推奨**
- CLI操作が中心で、GUIでの管理に慣れている場合はやや取っつきにくい

### 費用目安
- 小規模な常時稼働（1インスタンス・最小構成）で**月0〜500円程度**
- Volumeの容量に応じて追加費用（数十円〜）
- **合計：月0〜1,000円程度（アクセス次第で変動）**

### 運用開始までの工数
2〜4時間程度（アカウント作成30分＋デプロイ1〜2時間＋Volume・.env設定30分〜1時間）

### 難易度
**低〜中。** CLIコマンドが中心で手順自体はシンプルだが、Volumeのマウント設定や`fly.toml`の理解が多少必要。

### デプロイ手順
1. `flyctl`をインストールし、`fly auth login`でアカウント作成・ログイン
2. プロジェクトディレクトリで`fly launch`を実行（既存Dockerfileを自動検出）
3. `fly volumes create`でSQLiteファイル保存用の永続ボリュームを作成
4. `fly.toml`でボリュームのマウントパスとメモリ割り当て（LibreOffice用に1GB以上を推奨）を設定
5. `.env`の内容を`fly secrets set KEY=VALUE`コマンドで登録
6. `fly deploy`でデプロイ
7. 独自ドメインを使う場合は`fly certs add <ドメイン>`を実行し、表示されたDNSレコードをドメイン管理会社（またはCloudflare）側で設定

## 案G: Google Cloud Run + Litestream【次点候補：費用を極限まで下げたい場合】

Dockerfileをそのままデプロイできるサーバーレスコンテナサービス。**SQLiteの永続化が最大の論点**になる案のため、詳しく検証する。

### なぜ当初の案から外れていたか
Cloud Runは「サーバーレス＝ディスクは使い捨て（エフェメラル）」という設計が前提。SQLiteのような**ファイル1つに書き込み続けるDB**とは根本的に相性が悪く、「Cloud SQL（マネージドDB）と組み合わせるのが定石」という位置づけのため、比較から漏れやすい。ただし、以下の対策を講じれば費用最優先の観点で有力な選択肢になる。

### できること・担当範囲
Cloud Runが**ドメイン以外のほぼすべて**（アプリ実行、オートスケール、Secret Manager経由の.env管理）を担う。SQLiteの永続化のみ追加でCloud Storageの構成が必要。

### メリット
- Dockerfileがそのまま使え、GCPの中でも特に手厚いドキュメント・実績がある
- 従量課金で、アクセスが少ない間は非常に安価（月数百円程度に収まることが多い）
- **Litestreamを使えばSQLiteの変更が自動でGCSにバックアップされ、バックアップ運用が標準で組み込まれる**

### デメリット・注意点
- Cloud Runの標準ディスクはエフェメラルで、そのままではSQLiteのデータが消える
- 「GCS FUSEでの直接マウント」は公式・実際の検証プロジェクトの両方で「実験的・本番非推奨」と明記されており、書き込みが多いとデータ破損リスクがある → **この方式は推奨しない**
- **インスタンス数を必ず1に固定する必要がある**（複数インスタンスの同時書き込みによる整合性崩壊とStreamlitの状態保持問題を避けるため）
- Litestreamの導入・監視という追加の技術ハードルがある

### 解決策：Litestreamによるレプリケーション（推奨方式）
GCS FUSE直接マウントの代わりに、**Litestream**というOSS（無料）を使う。SQLiteのWAL（変更ログ）をAPI経由で監視し、変更差分を継続的にGCSへストリーミングでバックアップする仕組みで、ファイルシステムとして直接マウントするより構造的にデータ破損リスクが低い。

- **仕組み:** コンテナ内でLitestreamを起動し、SQLiteの変更を監視して自動的にGCSへ差分アップロード
- **復旧:** インスタンス再起動時は、起動スクリプトで先に`litestream restore`を実行してからStreamlitを起動する設計にする
- **費用:** Litestream自体は無料（OSS）。GCSの保存費用のみ（月数十円程度）
- **評価:** SQLiteを本番運用するための定番ツールとして広く使われており、GCS FUSE直接マウントより信頼性が高い

### 費用目安
- Cloud Run本体：小規模アクセスなら**月0〜500円程度**（無料枠あり）
- Cloud Storage（Litestream用バケット）：数十円〜
- **合計：月数百円程度（GCPの中では最安クラス）**

### 運用開始までの工数
1日程度（プロジェクト作成・Artifact Registry設定1時間＋デプロイ1〜2時間＋Litestream導入・動作検証半日程度）

### 難易度
**中〜高。** デプロイ自体はシンプルだが、Litestreamの導入・インスタンス数固定・復旧動作の検証など、他案より技術的な考慮点が多い。

### デプロイ手順（Litestream方式）
1. GCPプロジェクトを作成し、Artifact Registry（コンテナイメージ置き場）を有効化
2. Dockerfileに**Litestreamのバイナリと設定ファイル、起動スクリプトを追加**（既存のPython/LibreOffice部分は変更不要）
3. 起動スクリプトで「Litestreamが GCSから最新のSQLiteファイルを`restore`」→「Streamlitアプリを起動」→「Litestreamがバックグラウンドで変更を監視・レプリケート」の順で動くよう構成
4. SQLite保存・レプリケーション用にCloud Storageバケットを作成
5. `gcloud builds submit`でイメージをビルド・登録
6. `gcloud run deploy`でCloud Runにデプロイ（**インスタンス数の最大値を1に設定**）
7. Litestreamの設定ファイルでGCSバケットへのレプリケーション先を指定し、Cloud Run側にGCSアクセス権限（サービスアカウント）を付与
8. `.env`の内容はSecret Managerに登録し、Cloud Runの環境変数としてSecret参照する形で設定
9. Cloud Runが発行するURL（`https://xxx.run.app`）で動作確認
10. 独自ドメインを使う場合はCloud Run側でカスタムドメインのマッピングを設定し、Cloudflareまたはドメイン管理会社側でCNAMEを設定
11. **本番投入前に、想定の同時アクセス数でSQLiteへの書き込みテスト＋インスタンス再起動時の`restore`動作を必ず確認する**

## 案A: VPS単体（Cloudflare不使用）

最安クラスのVPSを1台契約し、Docker・Streamlit・SQLite・LibreOffice・.envをすべてそこに同居させる構成。**案Bとほぼ同額でCDN・WAFが付かないだけ**のため、優先度は案Bに劣る。

### できること・担当範囲
VPS1台が**ドメイン以外の全て**を担う。

### メリット
- 構成がシンプルで管理対象が1つ
- SQLiteのファイルはVPSのディスクにそのまま置けるため、永続化の不安が一切ない
- 月額固定費用のため予算が読みやすい

### デメリット
- CDN・WAF（不正アクセス対策）がない。DDoS等への耐性が低い
- SSL証明書は自分で発行・更新設定が必要（Let's Encrypt、無料だが手間はかかる）
- サーバーの保守（OSアップデート、障害対応）を自社で行う必要がある

### 費用目安
月換算で約600〜1,300円程度（VPS500〜1,200円＋ドメイン年1,000〜2,000円）

### 運用開始までの工数
半日〜1日程度

### 難易度
**中。** Linuxサーバーの基本操作が必要。

### デプロイ手順
1. VPSを契約し、Ubuntu等でサーバーを立てる
2. `apt update && apt install docker.io docker-compose`でDocker環境を構築
3. 既存のDockerfileと`docker-compose.yml`をサーバーに配置（SQLiteファイルはホスト側ディレクトリへボリュームマウント）
4. `.env`ファイルをサーバー上に直接配置
5. `docker compose up -d`でコンテナを起動
6. ドメインを取得し、VPSのグローバルIPにAレコードを設定
7. Nginxをリバースプロキシとして設定し、80/443番ポートでStreamlit（8501番）へ振り分け
8. Certbot（Let's Encrypt）でSSL証明書を取得し、自動更新のcronを設定
9. `ufw`等でファイアウォールを設定
10. SQLiteファイルの定期バックアップ用cronジョブを設定

## 案D: Railway

GitHubリポジトリを連携するだけで自動デプロイされる、開発体験重視のPaaS。

### できること・担当範囲
Railwayが**ドメイン以外のほぼすべて**を担う。

### メリット
- GitHub連携のみでビルド・デプロイが完結し、導入が最も簡単な部類
- 環境変数（.envの内容）をダッシュボードのGUIで設定でき、扱いやすい
- Volumeで永続化に対応

### デメリット
- **無料枠がなく**、利用開始時点から少額課金が発生する
- 完全従量課金のため、Spend Cap（上限設定）を必ず設定する必要がある
- 日本リージョンの提供がなく、レイテンシがやや不利
- **最小メモリプランではLibreOfficeのOOMリスクに注意**

### 費用目安
Hobbyプランで$5/月のクレジット付与（約750円前後）、超過分は従量課金

### 運用開始までの工数
1〜2時間程度（最も早い）

### 難易度
**低。** GUI操作が中心。

### デプロイ手順
1. GitHubにリポジトリ（Dockerfile含む）をプッシュ
2. Railwayにログインし、「New Project」からGitHubリポジトリを連携
3. Railwayが自動的にDockerfileを検出しビルド・デプロイを開始
4. 「Variables」タブで.envの内容を登録
5. 「Volumes」機能を追加し、SQLiteファイルの保存先ディレクトリをマウント
6. メモリプランをLibreOffice用に1段階上げる
7. 「Settings」から必ず「Usage Limit（Spend Cap）」を設定
8. 独自ドメインを使う場合は「Settings」→「Networking」から追加し、CNAMEをドメイン管理会社（またはCloudflare）側で設定

## 案E: Render（見送り推奨）

Heroku的な体験に近い、固定料金制のPaaS。

### できること・担当範囲
Renderが**ドメイン以外のほぼすべて**を担う。永続ディスクは有料プランのみ対応。

### メリット
- 無料プランがあり、検証用途であれば費用ゼロで試せる
- 有料プランは固定料金制で費用の見通しが立てやすい

### デメリット
- **無料プランは15分操作がないとスリープし、永続ディスクもないため今回の要件を満たせない**
- SQLiteの永続化には有料プラン（$7/月〜）が必須で、費用面の優位性が薄い
- 日本リージョンがない

### 費用目安
有料プラン（Persistent Disk利用）：$7/月〜（約1,050円〜）

### 運用開始までの工数
1〜2時間程度

### 難易度
**低。**

### デプロイ手順
1. GitHubにリポジトリ（Dockerfile含む）をプッシュ
2. Renderにログインし、「New Web Service」からリポジトリを連携
3. Dockerfileを自動検出させ、有料プラン（Persistent Disk対応インスタンス）を選択
4. 「Environment」タブで.envの内容を登録
5. 「Disks」機能でSQLiteファイル保存用のディスクをマウント
6. デプロイを実行し、動作確認
7. 独自ドメインを使う場合は「Settings」→「Custom Domain」から追加

## 案F: Cloudflare Containers（見送り推奨・参考記載）

Cloudflare上でDockerコンテナを直接動かす、2026年4月GAの新しいサービス。「Cloudflare必須ではない」という前提のため参考扱い。

### できること・担当範囲
Cloudflareが**ドメイン・CDN・WAF・アプリ実行のすべて**を担う。

### メリット
- ドメイン・CDN・WAF・アプリ実行のすべてを1つの契約で完結できる
- Dockerfileをそのまま利用可能

### デメリット
- **最大のネック：コンテナのディスクは基本的にエフェメラルで、SQLiteファイルを安定して永続化する標準的な方法がまだ確立されていない**
- 従量課金のため、常時稼働のStreamlitアプリでは費用が読みにくい
- サービス自体が新しく、情報・実績が少ない

### 費用目安
従量課金（Active-CPU課金）：月数百円〜だが、稼働時間次第で大きく変動。事前のPoCでの実測が必須。

### 運用開始までの工数
1〜2日程度（他案より長い）

### 難易度
**高。**

### デプロイ手順（参考）
1. Cloudflareの有料プラン（Workers Paid）を契約
2. `wrangler` CLIをセットアップし、`wrangler containers build`でイメージをビルド
3. `wrangler.toml`でインスタンスタイプ、スリープ時間を設定
4. コンテナを呼び出すWorkerコードを実装
5. SQLiteファイルの永続化方法を個別に検証・設計（標準的な解決策がないため独自対応が必要）
6. `.env`相当の設定は`wrangler secret put`で登録
7. `wrangler deploy`でデプロイ
8. 本番投入前に、LibreOffice変換処理とSQLite書き込みを含めた負荷テストを実施（必須）

## まとめ

費用・SQLiteの安全性・運用の手間の3軸で総合的に見て、**「案B：VPS + Cloudflare（無料枠）」を第一推奨**とする。サーバー運用にある程度慣れているならこの案が最もバランスが良い。運用工数をさらに削りたい場合は**案C：Fly.io**、GCPのエコシステムやコスト最小化を突き詰めたい場合は**案G：Cloud Run + Litestream**を代替候補として検討したい。
