## 1. はじめに

### 1.1 本書の位置づけ

本書は「勤怠管理システム 要件定義書」（v0.14）に基づき、実装に着手できるレベルまで詳細化した基本設計書である。画面項目、データベース（アプリケーションサーバー側データストア）のテーブル構成、Streamlitアプリ内の関数・モジュール構成（API設計に相当）、Excel連携方式、バリデーションロジック、排他制御ロジックを定義する。

### 1.2 前提

- 要件定義書に記載の確定事項をすべて前提とする。特に以下は設計全体に影響する重要事項である。
  - 技術構成：**Streamlit（Python）一体型**（フロント・バック分離なし）
  - OneDriveアクセス：**Graph API不使用、共有URL経由**、ルートディレクトリ1つの共有URLを起点とする
  - **一般ユーザーとadminの編集可能条件は排他的**（ロックされていない月＝一般ユーザーのみ編集可、ロック中の月＝adminのみ編集可）
  - ユーザーマスタ・ロック状態は、OneDriveではなく**アプリケーションサーバー側データストア**で管理
- 稼働時間帯：クラウド環境上で**常時稼働**を前提とする（時間帯を限定した稼働・停止の制御は設けない）
- 本書における「Streamlitアプリ」は、フロントエンド（画面）とバックエンド（ロジック）を兼ねる単一Pythonアプリケーションを指す。「API設計」の章は、REST APIではなく、アプリ内部の関数・モジュール間のインターフェース設計を指す（4章の技術構成に準拠）。

### 1.3 用語

要件定義書 2章の用語定義を継承する。加えて本書では以下を用いる。

| 用語 | 説明 |
|---|---|
| セッション状態 | Streamlitの`st.session_state`。ログイン中ユーザー情報、選択中の月、編集モードか否か等を保持する |
| アプリDB | ユーザーマスタ・ロック状態を保存するアプリケーションサーバー側のデータストア（本設計ではSQLite想定。13章参照） |
| 原本シート | 月次Excelファイル内の実データシート（要件定義書2章参照） |

### 2.2 レイヤー構成方針

実装をStreamlit単一アプリ内で行うが、保守性のためコード上は以下のレイヤーに分割する（要件定義書1.3節「Streamlit一体型」と矛盾しない。プロセス・デプロイ単位は1つのままとする）。

| レイヤー | 役割 | 主な内容 |
|---|---|---|
| 画面レイヤー | 画面表示・入力受付 | ログイン画面、勤怠入力・閲覧画面、admin各画面 |
| 業務ロジック層 | バリデーション・排他制御・業務ルール | 4.6節バリデーション、13章排他制御ロジック |
| 連携レイヤー | 外部リソースとの入出力 | OneDrive読み書き（共有URL経由）、Excel読み書き（openpyxl）、アプリDB読み書き、PDF生成 |

### 2.3 主要な処理方式（要点整理）

| 項目 | 方式 |
|---|---|
| OneDrive通信 | 共有URL（誰でも編集可能なリンク）経由。認証・アプリ登録不要 |
| Excelファイル読み書き | `openpyxl`によるセル単位の読み書き（書式を保持するため`load_workbook(keep_vba=False)`＋該当セルのみ`.value`更新。シート全体の再構築は行わない） |
| 認証 | 独自ID（社員番号）・パスワード（ハッシュ化）によるセッションベース認証 |
| ロック状態・ユーザーマスタ | アプリDB（SQLite等）で管理。OneDriveには置かない |
| PDF生成 | openpyxlでExcelのセル値・書式情報を読み取り、ReportLabでPDFを直接生成（9章参照） |


- ログイン後に表示される画面（サイドバーに並ぶメニュー項目）は、**role（`admin`／`general`）によってあらかじめ異なる一覧が組み立てられる**（3.3.1節参照）。一般ユーザーのサイドバーには「勤怠入力・閲覧」「パスワード変更」のみが並び、SC-03〜SC-06（admin専用画面）へのリンクは最初から存在しない。逆にadminのサイドバーには「勤怠閲覧・編集」「PDF出力」「ロック管理」「ユーザー管理」「パスワード変更」が並び、SC-02（一般ユーザー用勤怠入力）へのリンクは存在しない。
- 上記いずれの画面間の移動も、ブラウザを再読み込みしたり再ログインしたりする必要はない（3.3.1節「画面遷移とセッション維持の関係」参照）。

### 3.3 共通レイアウト方針

- Streamlitの`st.sidebar`にユーザー情報（氏名・役割）、ログアウトボタン、admin用メニューを配置する。
- 一般ユーザーのサイドバーには「勤怠入力」「パスワード変更」「ログアウト」のみを表示する。
- 画面の状態（プレビュー中／編集中）は`st.session_state["mode"]`（`"preview"` / `"edit"`）で管理する。

#### 3.3.1 画面アクセス制御（権限による表示・遷移制限）（置き換え）

- **一般ユーザーには、admin専用画面（SC-03〜SC-06）へのメニュー項目自体を表示しない。** adminには、一般ユーザー専用の勤怠入力・閲覧画面（SC-02）へのメニュー項目を表示しない。実装は、Streamlit標準の`st.navigation()`／`st.Page()`機能を用い、**ログイン中ユーザーのrole（`admin`／`general`）に応じて、サイドバーに渡すページ一覧そのものを動的に組み立てる**方式とする（`app.py`内の`_build_navigation()`が担う）。
  - 一般ユーザーの場合：ページ一覧に含めるのは「勤怠入力・閲覧」「パスワード変更」のみ。
  - adminの場合：ページ一覧に含めるのは「勤怠閲覧・編集」「PDF出力」「ロック管理」「ユーザー管理」「パスワード変更」のみ（adminは自身の勤怠データを持たないため、勤怠入力・閲覧は含めない）。
  - この方式により、一覧に含まれないページはサイドバー上にリンクとして描画されず、「リンクは見えるが押すとエラーになる」という中途半端な状態を避けられる。
- **メニュー非表示だけに依存せず、各ページ（`pages/*.py`）側でも権限チェックを行う二重の制御とする。** URLを直接指定される等の迂回アクセス対策として、各ページファイルの冒頭で`session_service`モジュール（5.2.7節参照）が提供する以下のいずれかの関数を呼び出す。
  - `require_login()`：ログイン必須画面共通。未ログインならエラー表示のうえ`st.stop()`で処理を中断する。
  - `require_admin()`：admin専用画面（SC-03〜SC-06）で使用。ログインしていない、またはroleが`admin`でない場合は「このページを表示する権限がありません」を表示し処理を中断する。
  - `require_general_user()`：一般ユーザー専用の勤怠入力・閲覧画面（SC-02）で使用。adminがこの画面へ到達した場合は、SC-03（勤怠閲覧・編集）の利用を案内し処理を中断する。
- 権限チェックに失敗した場合の挙動：エラーメッセージを表示したうえで`st.stop()`により以降の描画・処理を行わない。ページ全体の内容が一切表示されないため、権限のない情報が画面に一瞬でも描画されることはない。

**画面遷移とセッション維持の関係（新規追加）**

- `st.navigation()`によるページ間の移動は、同一ブラウザタブ・同一WebSocket接続内で行われるため、`st.session_state`（ログイン中ユーザー情報の保持先）は移動のたびに破棄されることなく維持される。**画面を行き来してもログインが切れることはない。**
- セッションが切れる（ログイン情報が破棄される）のは以下のケースに限られる。
  - ユーザーが「ログアウト」ボタンを押した場合（`session_service.end_session()`が呼ばれる）
  - ブラウザのタブを閉じる等でWebSocket接続が切断された場合
  - アプリケーションサーバー自体が再起動した場合（`st.session_state`はサーバーのメモリ上にのみ存在し、永続化されない）
- ログイン状態および現在のユーザー情報への読み書きは、`st.session_state`のキーを画面ごとに個別に扱うのではなく、**`session_service`モジュールに一元化する**（5.2.7節参照）。これにより、キー名の不整合や管理漏れを防ぐ。

## 4. データベース設計

要件定義書 5.4節・4.8節に基づき、アプリケーションサーバー側データストア（アプリDB）のテーブルを設計する。実装方式に指定はないため、開発のしやすさを優先し**SQLite**を採用する（要件定義書5.4節・4.8節「実装方式に指定はなく、実装のしやすさを優先して選定してよい」に基づく方針。本番クラウド環境でもファイルベースで運用可能であり、想定利用者数10名以下の規模に対して十分）。

### 4.1 データストア方針

| 項目 | 内容 |
|---|---|
| 種類 | SQLite（ファイルDB：`app.db`） |
| 保存場所 | アプリケーションサーバー（クラウド環境）のディスク上。OneDriveには置かない |
| 管理対象 | ユーザーマスタ（`users`テーブル）、ロック状態（`locks`テーブル） |
| 接続方法 | Python標準の`sqlite3`、またはORM（`SQLAlchemy`）のいずれかを利用可（実装フェーズで選定） |
| バックアップ | クラウド環境側のディスクスナップショット等に依存する運用とし、本設計では仕組みとしては定義しない（非機能要件に明記なしのため） |

### 4.2 ER図（概念）

```
┌─────────────────┐        ┌─────────────────────┐
│      users        │        │        locks          │
├─────────────────┤        ├─────────────────────┤
│ PK employee_id    │        │ PK id (autoincrement)│
│    last_name       │        │    target_month(YYYYMM)│
│    first_name      │        │ FK  employee_id       │
│    department      │        │    is_locked (bool)   │
│    password_hash   │        │    locked_at          │
│    role            │        │    unlocked_at        │
│    created_at      │        └─────────────────────┘
│    updated_at      │                 │
└─────────────────┘                 │
        │                             │
        └── employee_id で参照 ────────┘
```

- `users.employee_id`（社員番号）が`locks.employee_id`の論理的な外部キーとなる（SQLiteでもFK制約は定義可能）。
- 1ユーザー・1対象月につき`locks`のレコードは1件（一意制約：`UNIQUE(employee_id, target_month)`）。
- このほか、他テーブルと関連を持たない独立したテーブルとして`settings`（システム設定、運用開始月等を保持）を持つ（4.3.3節参照）。

### 4.3 テーブル定義

#### 4.3.1 `users`（ユーザーマスタ）

要件定義書5.4節の管理項目に対応。

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---|---|---|
| employee_id | TEXT | NOT NULL | PK | ログインID。一般ユーザーは社員番号（半角数字、桁数可変、0埋めなし）、**adminは固定値`admin`** |
| last_name | TEXT | NOT NULL | - | 姓 |
| first_name | TEXT | NOT NULL | - | 名 |
| department | TEXT | NOT NULL | - | 派遣先部署名（ユーザーごとの固定値） |
| password_hash | TEXT | NOT NULL | - | ハッシュ化パスワード（bcrypt等。10.2節参照） |
| role | TEXT | NOT NULL | CHECK(role IN ('admin','general')) | 権限区分 |
| created_at | TEXT | NOT NULL | - | 作成日時（ISO8601文字列） |
| updated_at | TEXT | NOT NULL | - | 更新日時（ISO8601文字列） |

**DDL（参考）**

```sql
CREATE TABLE users (
    employee_id   TEXT PRIMARY KEY,
    last_name     TEXT NOT NULL,
    first_name    TEXT NOT NULL,
    department    TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    role          TEXT NOT NULL CHECK(role IN ('admin','general')),
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
```

> 備考：adminアカウントは1名固定（要件定義書3.1節）とし、**ログインID（`employee_id`）は固定値`admin`とする**。初期構築時にDBへ直接1件だけ投入し、以後SC-06（ユーザーマスタ管理画面）からadmin権限のユーザーを新規作成する機能自体を設けない（3.9節参照）。これにより1名運用をシステム的に担保する。

#### 4.3.2 `locks`（ロック状態管理）

要件定義書4.8節に対応。

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---|---|---|
| id | INTEGER | NOT NULL | PK AUTOINCREMENT | 内部ID |
| target_month | TEXT | NOT NULL | - | 対象月（`YYYYMM`形式） |
| employee_id | TEXT | NOT NULL | FK → users.employee_id | 対象ユーザー |
| is_locked | INTEGER | NOT NULL | DEFAULT 0（0=未ロック、1=ロック中） | ロック状態 |
| locked_at | TEXT | NULL | - | 直近ロック日時 |
| unlocked_at | TEXT | NULL | - | 直近解除日時 |
| updated_at | TEXT | NOT NULL | - | 楽観的排他制御用（13.4節・admin操作競合対策） |

**DDL（参考）**

```sql
CREATE TABLE locks (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    target_month  TEXT NOT NULL,
    employee_id   TEXT NOT NULL REFERENCES users(employee_id),
    is_locked     INTEGER NOT NULL DEFAULT 0,
    locked_at     TEXT,
    unlocked_at   TEXT,
    updated_at    TEXT NOT NULL,
    UNIQUE(target_month, employee_id)
);
```

**レコードのライフサイクル**

- 該当月・該当ユーザーの`locks`レコードが存在しない場合は「未ロック」とみなす（レコードなし＝未ロックがデフォルト）。
- 「まとめてロック」実行時：対象月の全ユーザーについて、レコードが存在しなければINSERT（is_locked=1）、存在すればUPDATE（is_locked=1, locked_at更新）。
- 「個別に解除」実行時：該当レコードをUPDATE（is_locked=0, unlocked_at更新）。レコード自体は削除しない（履歴的な意味合いは持たないが、実装をシンプルにするため）。

#### 4.3.3 `settings`（システム設定）

3.5.2節「対象年月の選択制御」で用いる運用開始月等、システム全体で1件のみ持つ設定値を管理する。

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---|---|---|
| key | TEXT | NOT NULL | PK | 設定キー |
| value | TEXT | NOT NULL | - | 設定値 |
| updated_at | TEXT | NOT NULL | - | 更新日時 |

**DDL（参考）**

```sql
CREATE TABLE settings (
    key         TEXT PRIMARY KEY,
    value       TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);
```

**初期投入データ**

| key | value | 説明 |
|---|---|---|
| `service_start_month` | `YYYYMM`形式（例：`202608`） | 運用開始月。この月より前の月は一般ユーザー・adminともに選択・閲覧できない（3.5.2節） |

> 運用開始月は初期構築時に1回設定する想定とし、通常運用フェーズで変更する画面は設けない（変更が必要な場合はDBを直接更新する運用とする）。

### 4.4 インデックス方針

| テーブル | インデックス | 目的 |
|---|---|---|
| users | PRIMARY KEY(employee_id) | ログイン認証時の検索 |
| locks | UNIQUE(target_month, employee_id) | ロック状態の一意特定・重複防止 |
| locks | INDEX(target_month) | ロック管理画面（SC-05）での月単位一覧取得の高速化 |

### 5.2 主要関数インターフェース

#### 5.2.1 auth_service（置き換え：概要説明を追加）

**概要**

「ログインできるか」「パスワードを変えていいか」を判断する専用モジュール。画面側（`app.py`・`pages/`配下）はこのモジュールの関数を呼ぶだけで済み、パスワードをどう暗号化するか・DBのどのテーブルを見るか、といった具体的な処理には関与しない（画面とロジックを分離する設計方針）。

このモジュールが担う役割は大きく3つ。

1. **パスワードの暗号化・検証**（bcryptライブラリを利用）。平文パスワードはDBに一切保存せず、常にハッシュ化した値のみ保存する。ハッシュ化は不可逆な変換のため、万が一DBが漏洩してもパスワードそのものは判明しない。
2. **ログイン認証（`authenticate`）**。社員番号（またはadmin固定ID）とパスワードを受け取り、DBに保存されているハッシュと一致するか確認する。一致すればユーザー情報を返し、一致しなければ`None`を返す。「IDが存在しない」のか「パスワードが違う」のかは区別して返さない（区別すると社員番号の存在有無が推測できてしまうため、セキュリティ上あえて同じ結果にしている）。
3. **パスワード変更・再設定**。`change_password`は本人が現在のパスワードを覚えている状態での変更、`reset_password_by_admin`は本人がパスワードを忘れた際にadminが強制的に新しいパスワードを設定する（要件定義書5.4節のフローに対応）。いずれの場合も、新しいパスワードがパスワードポリシー（10.3節）を満たしているかを保存前に必ず確認する。

#### 5.2.7 session_service（新規追加）

5.2.6（既存最後の項目）の後に、以下を新規追加する。

**概要**

「今どのユーザーがログイン中か」をアプリ全体で一貫して参照・更新するためのモジュール。ログイン状態はStreamlitの`st.session_state`に保持されるが、そのキー名を各画面ファイルがバラバラに直接読み書きすると、キー名のtypoや管理漏れが起きやすい。そのため`st.session_state`への読み書きをこのモジュールに集約し、他のコードは`is_logged_in()`・`get_current_user()`のような意味の分かる関数越しにアクセスする方針とする。

セッションが画面遷移で切れない理由は、StreamlitがブラウザのWebSocket接続を維持している間、サーバー側で`st.session_state`を保持し続ける仕組みによる。`st.navigation`／`st.Page`（3.3.1節参照）でページを切り替えても、同一のWebSocket接続・同一の`st.session_state`が使い回されるため、画面を移動してもログイン情報は保持されたままになる。

セッションが切れる主なケースは以下の3つに限られる。

- ユーザーが明示的に「ログアウト」ボタンを押した場合
- ブラウザのタブを閉じてWebSocket接続が切れた場合
- サーバー側アプリケーションが再起動した場合（`st.session_state`はメモリ上のみで永続化されない）

また、このモジュールは3.3.1節の「画面アクセス制御」を実現する`require_login()`・`require_admin()`・`require_general_user()`という関数も提供する。各画面（`pages/`配下）はこれらの関数を先頭で1回呼ぶだけで、ログインチェックと権限チェックの両方が統一的に効く。

**関数インターフェース**

| 関数 | 引数 | 戻り値 | 説明 |
|---|---|---|---|
| `start_session(employee_id, last_name, first_name, role)` | ログイン成功時のユーザー情報 | - | セッションにユーザー情報を保存する |
| `end_session()` | - | - | セッション情報を破棄する（ログアウト時） |
| `is_logged_in()` | - | `bool` | ログイン中かどうかを返す |
| `get_current_user()` | - | `SessionUser \| None` | ログイン中ユーザー情報を返す。未ログイン時はNone |
| `require_login()` | - | `SessionUser` | 未ログインならエラー表示＋`st.stop()`で処理を中断する |
| `require_admin()` | - | `SessionUser` | ログイン必須かつrole=adminを要求。満たさない場合は処理を中断する |
| `require_general_user()` | - | `SessionUser` | ログイン必須かつrole=generalを要求。adminが到達した場合は案内のうえ処理を中断する |

**データ型（`SessionUser`）**

```python

    employee_id: str
    last_name: str
    first_name: str
    role: str  # "admin" | "general"
    # プロパティ
    display_name: str   # "姓 名"（スペース区切り、画面表示用）
    is_admin: bool       # role == "admin" の判定結果
```

## 6. Excel連携設計

要件定義書 4.2節・4.3節・5.1節・5.2節・6章に基づく。

### 6.1 OneDriveアクセス方式

- Microsoft Graph APIは使用しない。**共有URL（誰でも編集可能なリンク）**を用いてファイルの読み書きを行う。
- 共有URLはOneDriveの**ルートディレクトリ1つ**に対して発行されたものを使用する（環境変数`ONEDRIVE_SHARE_URL`等で設定値として保持）。
- 共有URL経由でのファイル一覧取得・ダウンロード・アップロードは、OneDriveの公開APIエンドポイント（共有リンクをGraph APIの`shares`エンドポイントに変換する方式、または直接ダウンロードURLへの変換）を利用する。具体的なHTTPリクエスト仕様は実装フェーズで確定する（14章「未確定事項」参照）。
- ローカル開発環境・本番クラウド環境のいずれも同じ共有URL方式を使用し、`.env`で接続先を切り替え可能とする（要件定義書1.5節）。

### 6.2 ファイル・フォルダ構成

要件定義書5.1節のとおり。

```
OneDriveルートディレクトリ/
  ├─ 【会社名】勤務実績管理表_テンプレート.xlsx
  ├─ 202606/
  │   ├─ 【会社名】勤務実績管理表_202606_山田太郎.xlsx
  │   └─ ...
  ├─ 202607/
  │   └─ ...
```

### 6.3 月次ファイル生成処理（冪等性の実装方針）

`get_or_create_monthly_file(employee_id, target_month)` の内部フロー：

```
1. OneDrive上で対象月フォルダ（YYYYMM）の存在を確認する
   → 存在しない場合、フォルダ作成を試みる
   → 作成時に「既に存在する」エラーが返った場合、エラーとして扱わず
     既存フォルダをそのまま使う（4.2節：冪等な作成処理）
2. 対象ユーザー・対象月のExcelファイルの存在を確認する
   → 存在する場合：そのまま読み込んで返す（再生成しない）
   → 存在しない場合：
      a. テンプレートファイルを読み込む
      b. 「原本」シートと「記入例」シートのみをコピーする
         （「変更履歴」シートはコピーしない）
      c. 原本シートの C8・O5・AH4・AH5 を自動設定する
         （C8=対象月初日、O5=社員番号、AH4=部署名、AH5=氏名[全角スペース区切り]）
      d. ファイル名を生成する
         （【会社名】勤務実績管理表_YYYYMM_姓名.xlsx、姓名はスペースなし）
      e. OneDrive上の対象月フォルダへアップロードする
         → アップロード時に同名ファイルが既に存在する場合はエラーとせず、
           既存ファイルを使う（同時アクセスによる重複生成対策）
3. 生成/取得したファイルのハンドルを返す
```

### 6.4 セル読み書き方針（書式保持）

- `openpyxl.load_workbook(path)` でファイルを読み込む。
- 値の更新は対象セルの`.value`のみを変更する（`cell.value = xxx`）。行・列の挿入削除、スタイルオブジェクトの再代入は行わない。
- 条件付き書式・罫線・フォント・数式は、セルの値のみを変更する限り`openpyxl`によって保持される。ただし、**Excelの条件付き書式ルール自体を動的に生成・削除する処理は行わない**（既存ルールをそのまま活かす）。
- 保存時は`workbook.save(path)`後、OneDriveへの書き戻し（アップロード）を行う。

### 6.5 セル対応表（実装リファレンス）

要件定義書4.3節・7.4節・14章の内容を統合。

| フロント項目 | Excelセル位置 | データ型 | 備考 |
|---|---|---|---|
| 日付 | B14:B44 | 日付 | システム側で自動生成、Excel側は既存の数式/値をそのまま利用 |
| 休暇種類 | D14:D44 | 文字列（リスト選択） | 参照リスト：AY14:AY24 |
| 始業時間 | N列（該当行） | 時刻文字列（`H:MM`、先頭ゼロなし） | フロントは時・分を別入力→結合して書き込み |
| 終業時間 | Q列（該当行） | 同上 | 同上 |
| 離業時間 | AC列（該当行） | 同上 | 同上 |
| 自社工数内容 | AP列（該当行） | フリーテキスト | - |
| 部署名 | AH4 | 文字列 | 生成時に自動設定、以後編集不可 |
| 氏名 | AH5 | 文字列（全角スペース区切り） | 同上 |
| 社員番号 | O5 | 文字列 | 同上 |
| 対象月初日 | C8 | 日付（YYYY/MM/01） | 同上 |
| 入力対象外 | F11:G16, F18:H21 | - | システムからは参照・編集・上書きしない |
| PDF出力範囲 | J1:AQ50 | - | 9章参照 |

### 6.6 時刻データの変換方針

- フロントで受け取る値：`(時: int, 分: int)`のタプル（1分単位）。
- Excel書き込み時：`f"{hour}:{minute:02d}"`形式の文字列に変換して該当セルへ設定する（例：`9`時`30`分 → `"9:30"`）。先頭ゼロを付けないことを確認する処理を保存直前に実施する（要件定義書4.6節）。
- Excel読み込み時：セルの値（文字列 or 時刻型）をパースし、`(時, 分)`のタプルとしてフロントへ渡す。

## 7. バリデーション設計

要件定義書4.6節・7.4節に基づく詳細ロジック。フロント（入力の都度）・バック（保存直前）の二重チェックとする。

### 7.1 ルール一覧（実装ロジック）

| # | ルールID | 条件（疑似コード） | エラーメッセージ例 |
|---|---|---|---|
| 1 | VAL-01 | `date is None and leave_type is not None` | 「日付が存在しない行には休暇種類を入力できません」 |
| 2 | VAL-02 | `date is None and (start_time is not None or end_time is not None)` | 「日付が存在しない行には始業・終業時間を入力できません」 |
| 3 | VAL-03 | `leave_type in ["有休","長期連休","特別休暇","欠勤","振替休暇"] and (start_time is not None or end_time is not None)` | 「この休暇区分の日には始業・終業時間を入力できません」（逆順操作も同一ルールで検知） |
| 4 | VAL-04 | `weekday in ["土","日"] and leave_type is None and (start_time is not None or end_time is not None)` | 「休日に始業・終業時間が入力されています」 |
| 5 | VAL-05（例外） | `weekday in ["土","日"] and leave_type is not None` の場合、VAL-04は適用しない | - |

> 実装上、VAL-04とVAL-05は1つの条件式にまとめる：`weekday in ["土","日"] and leave_type is None and (時刻入力あり)` の場合のみエラーとする。

### 7.2 判定タイミング

| タイミング | 対象 | 実行内容 |
|---|---|---|
| 入力の都度（フロント） | 変更のあったセル・行 | `validate_entry()`を呼び出し、該当行のみ即時判定・表示更新 |
| 保存ボタン押下時（フロント→バック） | 月内全日分 | `validate_all()`を呼び出し、1件でもエラーがあれば保存を中止しエラー一覧を表示 |
| 保存直前（バック） | 月内全日分 | フロントを経由しない直接アクセスやバグ混入への保険として、バックエンドでも同一ロジックで再検証する |

### 7.3 入力コンポーネントレベルでの制御（予防的UI制御）

7.1節のルールに違反する組み合わせが起きにくいよう、入力コンポーネント自体を動的に制御する（3.5.3節参照）。

| 状況 | UI制御 |
|---|---|
| 休暇種類が休暇区分（有休等）に設定されている | 始業・終業の入力欄をdisabled化 |
| 曜日が土日かつ休暇種類未選択 | 始業・終業の入力欄をdisabled化 |
| 時刻入力済みの状態から休暇区分へ変更しようとした | disabled化はせず、変更自体は許可した上でエラー表示（要件定義書4.6節「逆方向も同様にエラー」の趣旨を反映：入力順序に依存しない検知とするため、UI制御による入力阻止ではなくエラー表示で対応する） |

### 7.4 時刻フォーマットのバリデーション

- 時：0〜23の整数、分：0〜59の整数（1分単位）をプルダウン等で選択させるため、形式的に不正な値はUI構造上入力できない（要件定義書4.6節）。
- バックエンド保存直前に、最終的な文字列（`H:MM`形式）が正規表現 `^([0-9]|1[0-9]|2[0-3]):[0-5][0-9]$` に一致することを再確認する（防御的プログラミング）。

## 8. 排他制御設計

要件定義書13章に基づく。

### 8.1 一般ユーザー×admin競合（構造的回避）

- 一般ユーザーは「ロックされていない月」のみ編集可、adminは「ロック中の月」のみ編集可という排他条件により、同一ファイルへの同時編集は原則発生しない（要件定義書13.1節）。
- 設計上は、この前提を**保存直前の必須チェック**として実装することで担保する（8.2節）。前提が崩れるケース（同時にロック状態が変化する等）に備え、性善説に頼らずロジックで保証する。

### 8.2 保存直前チェックのシーケンス（一般ユーザー）

```
[保存ボタン押下]
      │
      ▼
① validate_all(entries) を実行
      │  エラーあり → 保存中止、エラー一覧表示、終了
      ▼ エラーなし
② lock_service.is_locked(target_month, employee_id) を再取得
      │  True（ロック済み） → 保存中止
      │  「この月はロックされました。入力内容は保存できません」を表示
      │  入力内容は画面上に残す（消去しない）
      ▼ False（未ロック）
③ attendance_service.save_attendance() 実行
      │  Excelセル更新 → OneDriveへ書き戻し
      ▼
④ 保存完了メッセージ表示 → プレビューモードへ遷移
```

### 8.3 保存直前チェックのシーケンス（admin）

```
[保存ボタン押下]
      │
      ▼
① validate_all(entries) を実行
      │  エラーあり → 保存中止
      ▼ エラーなし
② lock_service.is_locked(target_month, employee_id) を再取得
      │  False（ロック解除済み） → 保存中止
      │  「この月のロックが解除されています。保存できません」を表示
      │  入力内容は画面上に残す
      ▼ True（ロック中のまま）
③ attendance_service.save_attendance() 実行
      ▼
④ 保存完了メッセージ表示 → プレビューモードへ遷移
```

### 8.4 月フォルダ・月次ファイルの同時生成競合

- 6.3節のとおり、フォルダ作成・ファイル生成は「存在確認→作成、失敗時は既存を使う」という冪等な実装とする。
- 実装上の注意：OneDrive共有URL経由のAPIが「同名ファイル作成時に上書きする」挙動か「エラーを返す」挙動かは、共有URLの実装方式確定後に検証する必要がある（14章「未確定事項」参照）。上書きされる場合は、アップロード前に存在確認を行い、存在する場合はアップロード自体をスキップするロジックとする。

### 8.5 admin操作同士の競合（同一adminの複数タブ等）

- 要件定義書13.4節に基づき、ロック状態・ユーザーマスタの更新時は、保存直前に対象データの`updated_at`を再取得し、自分が画面を開いた時点の値と比較する楽観的排他制御を行う。
- 不一致（＝他の操作で更新されている）の場合は保存を中断し、「他の操作により更新されています。最新の内容を確認してください」を表示し、最新データを再取得して画面へ反映する。

### 8.6 多重クリック・多重送信対策

- すべての保存系ボタン（勤怠保存・ロック操作・ユーザーマスタ更新・パスワード変更等）は、処理中`st.session_state`にフラグを立てボタンをdisabled化することで、同一操作の多重送信を防止する。

## 9. PDF出力設計

要件定義書4.7節・7.6節・9.1節に基づく。

### 9.1 出力範囲・仕様

| 項目 | 内容 |
|---|---|
| 出力範囲 | 原本シート `J1:AQ50` |
| 用紙サイズ | A4縦 |
| 単位 | 1ユーザー1PDFファイル |
| 複数選択時 | ZIP形式にまとめる |
| 保存 | OneDrive・サーバーいずれにも保存しない（都度生成しダウンロードのみ） |

### 9.2 実装方式

PDF生成は**案B：openpyxlでセル値を読み取り、ReportLabでPDFを1から組み立てる方式**を採用する。

| 項目 | 内容 |
|---|---|
| 採用理由 | サーバー環境にLibreOffice等の外部アプリケーションを必要とせず、Pythonライブラリのみで完結するため環境依存が少ない。Dockerイメージも軽量に保てる |
| トレードオフ | 罫線・セル結合・背景色等の再現をopenpyxlで読み取った書式情報をもとに自前で描画する必要があり、LibreOffice変換（案A）に比べて実装工数がかかる。完全にExcelと同一の見た目を再現することは目指さず、**帳票として実用上問題ない体裁**（罫線・列幅バランス・文字の可読性）を目標とする |
| 使用ライブラリ | `openpyxl`（セル値・列幅・行高・罫線情報の読み取り）、`reportlab`（PDF描画） |
| 日本語フォント | ReportLabは日本語フォントを標準搭載しないため、日本語対応フォント（例：IPAexフォント等のライセンス上組み込み可能なもの）をアプリに同梱し、明示的に登録して使用する（14章「未確定事項」参照：フォント選定は実装フェーズ序盤で確定） |

#### 9.2.1 実装方式に関するリスク対応方針（案Bで問題発生時の切り替え）

- 実装スケジュール上は**案B（ReportLab自前描画）で実装を進める**ことを前提とする。
- ただし、実装を進める中で以下のような問題が生じ、期間内での解決が難しいと判断した場合は、**案A（Excelファイルを外部アプリケーション経由でPDF変換する方式）へ切り替える**ことを許容する。
  - 罫線・結合セルの再現が実用に耐えるレベルに達せず、帳票として使い物にならない
  - ReportLabでのレイアウト計算（9.4節のA4収まり調整含む）が、想定より大幅に工数超過している
  - その他、案Bのままでは納期・工数の見通しが立たないと判断される場合
- 切り替えの判断基準：実装スケジュール上でPDF出力機能に割り当てた期間の**半分を経過した時点**で見た目・工数の両面から進捗を確認し、遅れが大きい場合は案Aへの切り替えを検討する（詳細な切り替え判断のタイミングはスケジュール側に明記する）。
- 案Aへ切り替える場合の変更点：サーバー環境に外部アプリケーション（LibreOffice等）を追加導入し、Dockerイメージへの組み込みが必要になる（13章「開発・実行環境」の構成に影響する）。切り替えが発生した場合は、本設計書の該当箇所（2.3節・9.2節・13章）を合わせて更新する。

### 9.3 処理フロー

```
1. 対象ユーザー・対象月を受け取る
2. OneDriveから対象Excelファイルを取得
3. openpyxlで原本シートの J1:AQ50 範囲を読み込む
   ・各セルの値
   ・列幅・行高（レイアウト計算用）
   ・罫線・結合セル情報（帳票の枠線再現用）
4. 読み取った内容をもとに、ReportLabでA4縦のPDFページを描画する
   ・セル値をテキストとして配置
   ・罫線情報をもとに表の枠線を描画
   ・結合セルは1つの領域として描画
5. 生成したPDFバイナリをメモリ上に保持する（一時ファイルは作らない、または生成後即削除する）
6. 単一ユーザー：PDFバイナリをそのままダウンロードレスポンスとして返す
   複数ユーザー：全PDFをZIPにまとめてダウンロードレスポンスとして返す
```

> 罫線・結合セルの再現度は実装フェーズで実際に出力しながら調整する前提とし、完成度の目安（どこまで作り込むか）は実装初期にサンプル出力を見て依頼者と合意する。

### 9.4 A4用紙1枚に収めるレイアウト調整

要件定義書4.7節の出力範囲（`J1:AQ50`）は列数・行数が多いため、そのままの文字サイズ・列幅で描画すると**A4縦1枚に収まらない可能性がある**。以下の方針でA4縦1枚に収める。

| 調整項目 | 方針 |
|---|---|
| 基本方針 | 出力範囲（`J1:AQ50`）の内容が必ず**A4縦1枚**に収まるよう、縮小・調整を行う。ページ分割は行わない |
| 列幅の調整 | Excel上の列幅比率をベースに、PDFページの印字可能幅（A4縦・上下左右マージンを除いた幅）へ比例配分する（列同士の相対的な幅バランスは維持する） |
| フォントサイズ | 行数（日数分、最大31行＋ヘッダー・合計欄）に応じて、印字可能高さに収まるようフォントサイズを動的に算出する。基準サイズ（例：8〜9pt程度）から必要に応じて縮小する |
| 最低限の可読性 | フォントサイズを縮小しても判読できないほど小さくならないよう、下限サイズ（例：6pt程度）を設け、それでも収まらない場合は列の間隔・余白を先に詰める調整を優先する |
| マージン | 上下左右のマージンは最小限（例：5〜10mm程度）に設定し、印字可能領域を最大化する |
| 実装方法 | ReportLabでのページ描画時に、①出力対象の総列幅・総行数を先に計算する→②A4縦の印字可能領域（幅・高さ）と比較し、縮小率を算出する→③算出した縮小率をフォントサイズ・列幅・行高に一律適用して描画する、という順序で実装する |

> 実際の縮小率・可読性は、実装フェーズでサンプルデータを用いて出力し、必要に応じて基準サイズ・下限サイズの数値を調整する（9.2.1節のとおり、案Bでの実現が難しいと判断した場合は案Aへの切り替えも検討する）。

## 10. 認証・パスワード設計

要件定義書4.1節・5.4節に基づく。

### 10.1 ログイン処理フロー

```
1. 社員番号・パスワードを受け取る
2. users テーブルから employee_id で該当レコードを検索
3. レコードが存在しない、またはパスワードハッシュが一致しない場合
   → 「社員番号またはパスワードが正しくありません」を表示（存在有無を区別しない）
4. 認証成功 → st.session_state にユーザー情報（employee_id, 氏名, role）を保存
5. role に応じて画面を出し分け
```

### 10.2 パスワードハッシュ化方式

- ハッシュアルゴリズム：**bcrypt**を採用する（Python `bcrypt`ライブラリ、ソルト自動生成・実装が容易・実績豊富なため）。
- 平文パスワードは一切DBに保存しない。

### 10.3 パスワードポリシー（バリデーション）

要件定義書5.4節のとおり。

| 項目 | 内容 |
|---|---|
| 最小文字数 | 8文字以上 |
| 最大文字数 | **64文字**（確定値。バリデーションで65文字以上はエラーとする） |
| 使用可能文字 | 半角英大文字・半角英小文字・半角数字・一部半角記号（`! # $ % & * + - . / : = ? @ ^ _`） |
| 使用不可文字 | 全角文字・制御文字・スペース |
| 文字種要件 | 英大文字・英小文字・数字のうち2種類以上を組み合わせ必須（記号は任意） |
| 適用場面 | 新規登録時、パスワード変更時（自分自身）、admin強制再設定時 |

**バリデーション疑似コード**

```python
import re

def validate_password_policy(password: str) -> list[str]:
    errors = []
    if len(password) < 8:
        errors.append("8文字以上で入力してください")
    if len(password) > 64:
        errors.append("64文字以内で入力してください")
    if not re.fullmatch(r"[A-Za-z0-9!#$%&*+\-./:=?@^_]+", password):
        errors.append("使用できない文字が含まれています")
    types_used = sum([
        bool(re.search(r"[A-Z]", password)),
        bool(re.search(r"[a-z]", password)),
        bool(re.search(r"[0-9]", password)),
    ])
    if types_used < 2:
        errors.append("英大文字・英小文字・数字のうち2種類以上を組み合わせてください")
    return errors
```

### 10.4 パスワード忘れ対応フロー（システム上の実装）

要件定義書5.4節「パスワードを忘れた場合の対応」に基づく。

- 本システムはパスワードリセットメール等の自己完結型機能を持たない。
- adminがSC-06（ユーザーマスタ管理画面）から対象ユーザーを選択し、`reset_password_by_admin()`を呼び出すことで新パスワードを直接設定する。
- 設定後の新パスワードは、adminの画面上に確認のため一度だけ表示し（設定直後の確認表示）、それ以降は表示しない。DBには即座にハッシュ化して保存する。

## 11. エラーハンドリング方針

| ケース | 対応 |
|---|---|
| OneDrive通信エラー（タイムアウト・共有URL失効等） | 「保存/読み込みに失敗しました。しばらくしてから再度お試しください」を画面に表示する。ユーザー入力内容は画面上に保持する |
| Excelファイル破損・想定外フォーマット | 「ファイルの読み込みに失敗しました。管理者に連絡してください」を表示 |
| DB接続エラー | 「システムエラーが発生しました」を表示する |
| バリデーションエラー | 画面上に行単位で明示（7章参照）、保存は中止するがシステムエラーとしては扱わない |
| ロック競合エラー | 8.2節・8.3節のとおり、専用メッセージで案内し入力内容は保持する |

> **本システムでは、操作履歴・障害調査用ログのいずれも保持しない方針とする。** 要件定義書6章の「監査ログ機能は設けない」に加え、アプリケーションのエラーログ・アクセスログ等についても永続的な保存は行わない（実行中のコンソール出力等、デプロイ環境が標準で持つ一時的な出力は本方針の対象外とする）。障害発生時の調査は、画面に表示されるエラーメッセージと、発生状況の聞き取りをもとに行う運用とする。
