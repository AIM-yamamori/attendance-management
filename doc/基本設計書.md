# 1. はじめに

## 1.1 本書の位置づけ
本書は「勤怠管理システム 要件定義書 v0.14」に基づき、実装済みのコード（`app.py`、`_pages/`配下6画面、`services/`配下8モジュール、`adapters/`配下3モジュール、DBスキーマ、Docker関連ファイル）と整合させた基本設計書である。

各`.py`ファイルに対応する節（3章・4章・5章・6章）の冒頭には、`> **概要**：`で始まる引用ブロックとして、そのファイルが「何を行うか」（責務・入出力・他モジュールとの関係）を簡潔に記載する。詳細な関数シグネチャ・処理フローはその後に続ける。

## 1.2 基本方針
- Webブラウザから利用する。
- StreamlitによるPython一体型アプリケーションとする。
- ユーザー情報・ロック状態・システム設定はSQLiteで管理する。
- 勤怠データ本体は月次Excelファイルとして管理する。
- ExcelファイルはOneDrive上で管理する。
- **OneDrive連携**: Microsoft Graph API の `/shares` エンドポイントを使用し、クライアントクレデンシャルフローで認証を行う（実装済み）。環境変数が未設定の場合はローカルディレクトリを疑似OneDriveとして使うフォールバックへ自動的に切り替わる。
- **Excel操作**: 表示（プレビュー・記入例）時は `data_only=True` で読み込み、計算結果キャッシュ値を取得する。保存時は `data_only=True` を使わず、数式を保持したまま対象セルの `.value` のみを更新する。
- **自動計算項目・合計欄**: Excel数式のキャッシュ値は保存直後にズレるため、休憩時間1・実働時間・超勤・休日出勤・深夜、および月末合計欄は、Excelの数式ロジックをPython側（`excel_adapter.calc_auto_values` / `attendance_service._calc_totals`）で再現し、都度再計算した値を画面に表示する。
- **権限分離**: 一般ユーザーとadminの編集可能状態を「ロック」によって構造的に排他的にする。
- パスワードはbcryptでハッシュ化し、平文では保存しない。
- **時刻入力方式**: 当初検討していた「時・分をプルダウンで別々に受け付ける」方式ではなく、`"9:00"`のような`H:MM`形式のテキストボックス1つに統一し、入力の都度サーバー側でサニタイズ（全角→半角変換、数字とコロン以外の除去）を行う方式で実装している（3.11節参照）。

# 2. システム全体構成

## 2.1 論理構成

```text
┌──────────────────────────────┐
│          Webブラウザ          │
│   一般ユーザー / admin 共通    │
└──────────────┬───────────────┘
               │ HTTPS
               ▼
┌──────────────────────────────────────────┐
│             Streamlit アプリ             │
│                                          │
│  ┌────────────┐   ┌──────────────┐      │
│  │ 画面レイヤー │ → │ Service層     │      │
│  │ _pages/    │   │ services/    │      │
│  └────────────┘   └──────┬───────┘      │
│                           │              │
│                    ┌──────┴──────┐       │
│                    │ Adapter層   │       │
│                    │ adapters/   │       │
│                    └───┬─────┬───┘       │
└────────────────────────┼─────┼───────────┘
                         │     │
              ┌──────────┘     └────────────┐
              ▼                             ▼
        ┌─────────────┐              ┌─────────────┐
        │ SQLite      │              │ OneDrive    │
        │ app.db      │              │ 月次Excel    │
        └─────────────┘              └─────────────┘
                                            ▲
                                            │
                              ONEDRIVE_TENANT_ID等が
                              未設定の場合は疑似OneDrive
                              （ローカルディレクトリ）へ自動フォールバック
```

## 2.2 レイヤー構成
- **画面レイヤー**（`_pages/`）: Streamlitによる画面表示、入力受付、結果表示。業務ロジックは持たず、Service層の呼び出しとエラーメッセージの表示に専念する。
- **Service層**（`services/`）: 認証、セッション管理、ユーザー管理、ロック、勤怠、バリデーション、PDF、設定の各業務処理。
- **Adapter層**（`adapters/`）: DB（SQLite）、OneDrive（Graph API／疑似OneDrive）、Excel（openpyxl）との入出力。
- **DB**: ユーザーマスタ、ロック状態、システム設定。
- **OneDrive**: 月次Excel、テンプレートExcel。

## 2.3 責務分離
画面側に業務ロジックを直接記述せず、可能な限りService層へ委譲する。実装済みの全画面（ログイン画面含む）はこの方針に沿い、バリデーション・ロック判定・Excel/OneDrive操作を一切持たない。

## 3.2 二重のアクセス制御
- **Navigationによる制御**: `st.navigation()` を利用し、ログイン状態およびroleに応じて動的にサイドバーを構成する（`app.py`の`_build_navigation()`）。一般ユーザーには「勤怠入力・閲覧」、adminには「勤怠閲覧・編集／PDF出力／ロック管理／ユーザー管理」のみを一覧に含める。パスワード変更は両者共通。
- **ページ内権限チェック**: 各ページ冒頭で `session_service.require_admin()` / `require_general_user()` / `require_login()` を実行し、メニュー非表示だけに頼らない二重チェックとする。
- **ログイン画面の特殊処理**: ログイン画面自体を `st.Page(..., position="hidden")` として登録し、ログイン前でも `st.navigation()` を呼び出すことで、Streamlitの「pages/ディレクトリ自動検出」を確実に無効化する（実ファイルは自動検出対象外の`_pages/`ディレクトリに配置）。
- **サイドバーのユーザー情報表示**（`_render_sidebar_user_info()`）: adminは氏名を表示せず「管理者」のみ表示する（adminは`姓=名="管理者"`として投入される特殊アカウントのため、`display_name`をそのまま出すと冗長になる）。一般ユーザーは氏名・社員番号を表示する。
- **ログアウト時のセッションクリア**: `st.session_state.clear()` を実行し、`st.navigation`の内部状態（直前に選択していたページ等）も含めて完全にリセットする。

## 3.3 SC-01 ログイン

`app.py`が担う。

> **概要**：本アプリのエントリポイント。ログイン画面の表示・認証処理に加え、アプリ初回起動時のDB初期化（スキーマ作成・adminアカウント投入）、ログイン後のロール別画面遷移制御（`st.navigation`によるサイドバー構成）を行う。他の全画面はこのファイル経由で呼び出される。

- 入力：ログインID（社員番号 / `admin`）、パスワード
- 認証は`auth_service.authenticate()`に委譲する。
- IDが存在しない場合とパスワードが違う場合でエラーメッセージを区別しない（「IDまたはパスワードが正しくありません」に統一）。
- 認証成功時は`session_service.start_session()`でセッションへユーザー情報を保存し、`st.rerun()`で画面を再描画する。

**アプリ初回起動時の初期化**（`_init_app()`）：
- `db_adapter.init_db()`でスキーマを冪等に作成する。
- 環境変数`INITIAL_ADMIN_PASSWORD`（未設定時は`"ChangeMe123"`）をハッシュ化し、`db_adapter.seed_initial_admin()`でadminアカウント（`employee_id="admin"`, 姓名="管理者", 部署="-"）を、存在しない場合のみ1件投入する。
- 環境変数`SERVICE_START_MONTH`が設定されていれば、`settings`テーブルの`service_start_month`キーへ、未設定の場合のみ初期値を投入する。

## 3.4 SC-02 勤怠入力・閲覧（一般ユーザー）

`_pages/01_attendance_input.py`が担う。`session_service.require_general_user()`によりadminのアクセスを遮断する。

> **概要**：一般ユーザーが自分自身の月次勤怠を閲覧・入力するための画面。対象年月選択→月次ファイル取得（存在しなければ生成）→プレビュー表示→編集モード切り替え→バリデーション→保存、という一連の流れをこのファイル1つで完結させる。休暇種類・始業/終業/離業時間・自社工数内容の入力欄と、H:MM形式テキストボックスのリアルタイムサニタイズ処理を持つ。記入例（ヘルプ）表示もこの画面から行う。



**基本フロー**
1. 対象年月を選択する（選択肢は`attendance_service.build_selectable_months()`による。運用開始月〜当月の翌月）。対象年月を切り替えると編集モードは自動的に解除する。
2. ヘッダー部に氏名・社員番号・部署名、ロック状態バッジ（🔒ロック中／🔓未ロック）、ヘルプボタンを表示する。
3. `attendance_service.get_or_create_monthly_file()`で月次ファイルを取得（存在しなければテンプレートから生成）し、`load_attendance()`で読み取る。
4. Excelヘッダー情報（派遣先企業名・部署名・社員番号・氏名・深夜開始時間・所定・午前・午後・休憩時間1〜3）を表示する。
5. 「編集する」ボタンでプレビュー表示と編集フォームを切り替える。ロック中は「編集する」ボタンが`disabled`になる。
6. 編集フォームで入力し、「保存する」を押すと`validation_service.validate_all()`でバリデーション後、`attendance_service.save_attendance(actor_role="general")`を呼び出す。

**ヘルプ表示**：ヘルプボタン押下で`show_help`フラグをトグルし、`attendance_service.load_example()`経由で記入例シートを読み取り専用テーブルとして表示する（3.10節参照）。

## 3.5 SC-03 勤怠閲覧・編集（admin）

`_pages/02_admin_attendance_edit.py`が担う。`session_service.require_admin()`でチェックする。

> **概要**：adminが任意の一般ユーザー・任意の月の勤怠を閲覧・編集するための画面。SC-02（一般ユーザー用）とほぼ同一のUI・編集ロジックを持つが、対象ユーザー選択欄が追加される点と、「編集する」ボタンの活性条件が一般ユーザーとは逆（ロック中のみ編集可）である点が異なる。プレビュー表示はロック状態に関わらず常時可能。



- SC-02とほぼ同一のUI構成だが、対象ユーザー選択欄（`user_service.list_users()`から一般ユーザーのみ選択可能）が追加される。
- 対象ユーザー・対象月のいずれかを切り替えると編集モードは自動的に解除する（`_admin_edit_context`キーで判定）。
- **重要：一般ユーザーとは逆に、「編集する」ボタンはロック中のファイルのみ活性化する**（`disabled=not is_locked`）。ロックされていないファイルはadminであっても編集モードに入れない。
- プレビュー表示（読み取り専用）は、ロック状態に関わらず常に可能。
- 保存時は`attendance_service.save_attendance(actor_role="admin")`を呼び出す。

## 3.6 SC-04 PDF出力

対象年月を切り替えると、選択状態・生成済みPDF/ZIPバイナリはリセットされる。

PDF

複数名

ZIP

## 3.7 SC-05 ロック管理

`_pages/04_admin_lock_management.py`が担う。

> **概要**：adminが対象月ごとに全ユーザーのロック状態を確認し、一括ロック・個別ロック・個別解除を行うための画面。ロック状態の判定・更新処理そのものは`lock_service`に委譲し、本ファイルは一覧表示（氏名・社員番号・状態バッジ・操作ボタン）と、誤操作防止のための一括ロック確認ダイアログ（`st.dialog`）の制御を担う。



**機能**
- 対象月選択（SC-02と同じ選択範囲）
- 全ユーザーのロック状態一覧表示（氏名・社員番号・状態バッジ・操作ボタン）

- 一括解除：なし（要件定義書4.8節。解除は必ず個別に行う）
- 個別解除：あり

**状態遷移**
```text

```

## 3.10 SC-08 記入例（ヘルプ）

SC-02・SC-03から「ヘルプ」ボタンで表示・非表示をトグルする独立画面ではなく、同一画面内のインライン表示として実装されている。

> **概要**：独立した`.py`ファイルは存在しない。`_pages/01_attendance_input.py`・`_pages/02_admin_attendance_edit.py`双方の内部に、ヘルプボタン押下時のみ描画される表示ブロックとして組み込まれている。データ取得は両画面共通で`attendance_service.load_example()`を呼び出す。

- `attendance_service.load_example()`は、`load_attendance()`と全く同じ処理経路（`excel_adapter.read_day_rows`・`read_header_values`・`calc_auto_values`）を、対象シートのみ`記入例`シートに差し替えて実行する。これにより自動計算列も含めて原本シートのプレビューと完全に同じ形式・精度で表示できる。
- 編集不可。`記入例`シートへの書き込みは一切行わない。
- `原本`と同じセル対応表（6.6節）を利用する。

> **実装上の注意（シート名）**：`excel_adapter.py`の定数`SHEET_KINYUREI`は`"記入例 "`（末尾に半角スペース1文字）と定義されている。テンプレートExcel内の実際のシート名がこの表記と完全一致している必要があり、シート名の末尾に空白がない場合は`KeyError`（シートが見つからない）となる。テンプレート更新時は要注意。

## 3.11 時刻入力の実装方式（H:MM テキストボックス）

要件定義書0.13節では「時・分を別要素（プルダウン等）で受け付け、コロン区切りテキストは採用しない」方針が示されていたが、**実装（`01_attendance_input.py`・`02_admin_attendance_edit.py`）では、この方針を採用せず、`"9:00"`のような`H:MM`形式のテキストボックス1つに統一している。** 本書はこの実装を正として記載する。

- 対象欄：始業時間・終業時間・離業時間（3欄とも同一方式）。
- 正規表現：`^([0-9]|1[0-9]|2[0-3]):[0-5][0-9]$`（`excel_adapter.validate_excel_time_string`と同一パターンを画面側でも共有）。
- **サニタイズ**：`on_change`イベントのたびに、`unicodedata.normalize("NFKC", text)`で全角数字・全角コロンを半角へ変換し、変換後に半角数字・半角コロン以外の文字を除去する。ブラウザのキー入力段階で物理的に制限することは`st.text_input`単体ではできないため、「入力直後の再描画で不正な文字が自動的に消える／半角化される」という体験になる。
- **StreamlitAPIException対策**：`on_change`で`st.session_state[key]`を書き換えるウィジェットには、`value`と`key`を同時に渡してはいけない制約があるため、ウィジェット生成前に`st.session_state`が未設定の場合のみ初期値を代入し、`st.text_input`呼び出し時は`key`のみを渡す（Session State一本化）。
- 空文字は「未入力」として扱う（`None`）。
- 解析結果が正規表現に一致しない場合は「形式が不正」としてフラグを立て、該当行を`st.error`で赤枠表示し、保存ボタンを無効化する。

# 4. データベース設計

## 4.1 DB方式

> **概要（`adapters/db_adapter.py`）**：SQLiteへの接続・クエリ実行を担う連携レイヤー。コネクション取得（`get_connection`）とwith文で使えるカーソル（`get_cursor`、コミット制御・例外時ロールバック込み）、スキーマ初期化（`init_db`）、初回起動時のadminアカウント・初期設定の冪等な投入（`seed_initial_admin` / `seed_setting_if_absent`）を提供する。SQLの生文字列を直接扱うのはこのモジュールのみとし、他のservice層はSQLを意識しない。

SQLiteを使用。接続先パスは環境変数`DB_PATH`（デフォルト`./data/app.db`）。Docker環境ではホストの`./data`を`/app/data`へマウントし永続化する。`db_adapter.get_connection()`は接続のたびに親ディレクトリを`os.makedirs`で作成し、`PRAGMA foreign_keys = ON`で外部キー制約を有効化する。

## 4.2 テーブル定義

`models/schema.sql`に定義。`db_adapter.init_db()`が起動時に`executescript`で冪等に適用する。

## 5.2 auth_service

> **概要**：「ログインできるか」「パスワードを変えてよいか」の判断を一手に引き受けるモジュール。パスワードのハッシュ化・検証（bcrypt）、ログイン認証、パスワードポリシー検証、本人によるパスワード変更、adminによる強制パスワード再設定を担う。画面側（`app.py`・`06_password_change.py`・`05_admin_user_management.py`）はこのモジュールの関数を呼ぶだけで、暗号化方式やDBのテーブル構造を意識しない。

責務：
- パスワードのハッシュ化・検証（bcrypt）
- ログイン認証
- パスワードポリシー検証
- 本人パスワード変更
- adminによるパスワード再設定

主要関数：
```python
hash_password(plain_password) -> str
verify_password(plain_password, password_hash) -> bool
validate_password_policy(password) -> list[str]  # 違反メッセージのリスト。空なら合格
authenticate(employee_id, password) -> Optional[User]
change_password(employee_id, current_password, new_password) -> tuple[bool, Optional[str]]
reset_password_by_admin(employee_id, new_password) -> tuple[bool, Optional[str]]
```

- `authenticate`：IDが存在しない場合と、パスワードが不一致の場合を区別せず`None`を返す（セキュリティ方針）。
- `validate_password_policy`：8文字以上64文字以内、使用可能文字は半角英大文字・英小文字・数字・一部記号（`! # $ % & * + - . / : = ? @ ^ _`）、英大文字・英小文字・数字のうち2種類以上の組み合わせを必須とする。
- `PASSWORD_MIN_LENGTH = 8`, `PASSWORD_MAX_LENGTH = 64`を公開定数として持つ（画面側のcaption表示で参照）。
- `User`データクラスは`full_name`（スペースなし）・`full_name_with_space`（全角スペース区切り）のプロパティを持つ。

## 5.3 session_service

> **概要**：「今どのユーザーがログイン中か」をアプリ全体で一貫して参照・更新するためのモジュール。`st.session_state`への読み書きをこのモジュールに集約し、画面側は「is_logged_in()」「require_admin()」のような意味の分かる関数越しにアクセスする。ログイン開始・終了（完全クリア）、ロール別のアクセス制御（3画面パターン：全員／admin限定／一般ユーザー限定）を提供する。

- st.session_stateへの読み書きを本モジュールに集約し、他コードはキー名を直接扱わない。
- `SessionUser`データクラス：`display_name`・`full_name_no_space`・`full_name_with_space`・`is_admin`のプロパティを持つ。
- **セッションの完全な破棄**：ログアウト時、`st.session_state.clear()`を実行する。ログイン関連キーのみのpopでは`st.navigation`の内部状態（選択していたページ等）が残り、ログアウト直後に旧ロールのサイドバーが一瞬残像表示される不具合があったため、完全クリア方式を採用している。
- 権限チェック関数：`require_login()`（未ログイン時はエラー表示して`st.stop()`）、`require_admin()`（adminでなければ`st.stop()`）、`require_general_user()`（adminがアクセスした場合は案内して`st.stop()`。adminは自身の勤怠データを持たないため）。

## 5.4 user_service

> **概要**：一般ユーザーのマスタ情報（`users`テーブルの`role='general'`レコード）に対するCRUD処理を担うモジュール。社員番号の重複チェック、パスワードポリシー検証（`auth_service`委譲）、ユーザー削除時の関連`locks`レコードの整合的な削除（外部キー制約対応）を行う。SC-06（ユーザー管理画面）から呼び出される。

責務：一般ユーザー（`role='general'`）のCRUD。

```python
list_users() -> list[User]          # role='general'のみ。adminは含まない
get_user(employee_id) -> Optional[User]
create_user(last_name, first_name, employee_id, department, initial_password) -> tuple[bool, Optional[str]]
update_user(employee_id, last_name, first_name, department) -> tuple[bool, Optional[str]]
delete_user(employee_id) -> tuple[bool, Optional[str]]
```

- `create_user`・`update_user`・`delete_user`は統一して`tuple[bool, Optional[str]]`（成功したか、エラーメッセージ）を返す。
- `delete_user`は`locks`テーブルの外部キー制約（`employee_id` REFERENCES `users(employee_id)`）に抵触しないよう、同一トランザクション内で`locks`を先に削除してから`users`を削除する。

## 5.5 lock_service

> **概要**：月×ユーザー単位のロック状態（`locks`テーブル）の取得・更新を担うモジュール。「レコードが存在しない＝未ロック」という暗黙のデフォルトルールをこのモジュール内に隠蔽し、呼び出し側（画面・`attendance_service`の保存処理）はロックの有無だけを意識すればよいようにする。一括ロック・個別ロック・個別解除（解除は個別のみ）を提供する。

```python
is_locked(target_month, employee_id) -> bool
lock_all(target_month) -> int          # 対象人数を返す
lock_one(target_month, employee_id) -> bool
unlock_one(target_month, employee_id) -> bool
list_lock_status(target_month) -> list[LockStatus]
```

- `is_locked`：レコードが存在しない場合は`False`（未ロック）を返す。
- `lock_all`・`lock_one`・`unlock_one`：いずれもUPSERT文（`INSERT ... ON CONFLICT DO UPDATE`）で実装。存在チェックと更新を1文で行う。
- 解除は個別解除のみ（`unlock_one`）。一括解除関数は設けない。

## 5.6 attendance_service

> **概要**：勤怠データの読み書き全体を統括するモジュール（本システムの中核）。ファイル名・フォルダ名の生成規則、対象年月の選択肢制御、月次ファイルの取得・新規生成（`excel_adapter`・`onedrive_adapter`の組み合わせ）、Excelからの読み取り結果を画面向けデータ（`AttendanceData`）に整形する処理、自動計算項目・合計欄のPython側再計算、編集内容の保存（ロック再チェック含む）を担う。SC-02・SC-03・SC-04（PDF出力）のいずれからも呼び出される、画面共通の中心的な業務ロジック層。

責務：
- ファイル名・フォルダ名の生成規則（会社名は環境変数`COMPANY_NAME`、未設定時は`"【会社名】"`）
- 対象年月の選択肢制御
- 月次ファイルの取得・新規生成（`get_or_create_monthly_file`）
- 勤怠データの読み取り（原本シート／記入例シート共通処理）
- 自動計算項目・合計欄の再計算
- 編集内容の保存（ロック再チェック含む）

主要関数：
```python
get_template_relative_path() -> str
build_monthly_file_name(target_month, full_name_no_space) -> str
build_monthly_file_relative_path(target_month, full_name_no_space) -> str
target_month_to_first_day(target_month) -> str        # "YYYY/MM/01"
target_month_to_date(target_month) -> datetime.date
build_selectable_months(today, service_start_month) -> list[str]
default_target_month(today) -> str
format_month_label(target_month) -> str                # "YYYY年MM月"
get_or_create_monthly_file(employee_id, target_month, full_name_no_space, full_name_with_space, department) -> WorkbookHandle
load_attendance(handle) -> AttendanceData               # 原本シート
load_example(handle) -> AttendanceData                  # 記入例シート（同一処理経路）
save_attendance(handle, edits, actor_role) -> None       # actor_role: "general" | "admin"
```

- **対象年月の選択範囲**（`build_selectable_months`）：`service_start_month`未設定時は当月のみ。設定時は`service_start_month`〜「当月の翌月」までの範囲を`YYYYMM`昇順で返す。下限が上限を上回る場合は上限（翌月）のみを返す。
- **月次ファイル取得**（`get_or_create_monthly_file`）：
  1. `onedrive_adapter.ensure_folder(target_month)`で月フォルダを冪等に用意する。
  2. `onedrive_adapter.file_exists()`で対象ファイルの有無を確認し、存在すればダウンロードしてハンドルを返す。
  3. 存在しなければテンプレートをダウンロードし、`excel_adapter.create_workbook_from_template()`で原本・記入例シートのみのワークブックを作り、`set_monthly_header_cells()`でC8・O5・AH4・AH5を自動設定し、ローカル保存後`onedrive_adapter.upload_file(..., overwrite=False)`でアップロードする（同時アクセス時は先着優先で上書きしない）。アップロード後、確定した内容を再ダウンロードしてローカルに反映する。
- **保存処理**（`save_attendance`）：ロック再チェック→Excel書き込み→ローカル保存→OneDriveへ`overwrite=True`でアップロード、の順に行う。ロック再チェックのルールは8.2節・8.3節参照。バリデーション（`validate_all`）は画面側で事前実施済みであることが前提。

## 5.7 validation_service

> **概要**：VAL-01〜VAL-05のバリデーションルール判定ロジックのみを持つ、状態を持たない純粋なモジュール。フロント側（入力の都度のリアルタイムチェック）とバック側（保存直前の一括再チェック）の両方から同一関数を呼び出すことで、判定ロジックの二重実装・ルールのズレを防ぐ。DBへの読み書きやExcel操作は一切行わない。

```python
validate_entry(row_index, date_value, weekday, leave_type, start_time, end_time) -> list[ValidationError]
validate_all(entries) -> list[ValidationError]
```

- `FULL_DAY_LEAVE_TYPES = ("有休", "長期連休", "特別休暇", "欠勤", "振替休暇")`（VAL-03対象。半休2種は対象外）。
- `validate_all`は`DayEntry`・`DayEditInput`いずれの型のオブジェクトでも、`row`（または`row_index`）・`date_value`・`weekday`・`leave_type`・`start_time`・`end_time`属性を`getattr`で参照するダックタイピングで動作する。

## 5.8 pdf_service

> **概要**：月次Excelファイルを、条件に合わせてPDF（またはZIP）に変換するモジュール。元ファイルには一切手を加えず、印刷範囲・用紙設定を施した一時コピーをLibreOfficeのheadlessモードで変換する処理をこのモジュール内に閉じ込める。`attendance_service`からデータを取得し、変換結果のバイナリのみを画面（SC-04）へ返す。生成物はOneDrive・サーバーいずれにも永続保存しない。

```python
generate_pdf(employee_id, target_month) -> bytes
build_pdf_file_name(employee_id, target_month) -> str
generate_zip(employee_ids, target_month) -> bytes
```

- 実装方式はLibreOffice経由の変換（9章参照）。当初検討していたreportlabによる自前描画方式は、罫線・数式依存項目（自動計算列・合計欄）の再現が困難であったため不採用としている。

## 5.9 settings_service

> **概要**：`settings`テーブルに保持する、システム全体で1件だけ持つキー・バリュー形式の設定値を読み書きする小さなモジュール。現時点では運用開始月（`service_start_month`）のみを扱うが、キーと値の組み合わせを汎用的に扱う作りにしており、将来の全体設定追加にも同じ関数群を使い回せる。

```python
get_setting(key) -> Optional[str]
set_setting(key, value) -> None
get_service_start_month() -> Optional[str]
```

- `KEY_SERVICE_START_MONTH = "service_start_month"`。将来的な全体設定の追加にも同一テーブル・同一関数群を使い回せる汎用設計。

# 6. Excel・OneDrive連携設計

## 6.1 シート構成

> **概要（`adapters/excel_adapter.py`）**：openpyxlを使ってExcelファイルの読み書きを行うアダプター。「テンプレートから月次ファイルを作る（原本・記入例シートのみコピー）」「セルの値だけを読み書きし書式を絶対に壊さない」「フロントの`(時, 分)`タプルとExcelの`H:MM`文字列を相互変換する」「日次データ・ヘッダー情報の読み取り」「自動計算列のPython側再現（`calc_auto_values`）」の5つを担う。OneDrive上のどこからファイルを取得するかは関知せず（`onedrive_adapter`の責務）、「1つのExcelファイルをどう読み書きするか」にのみ関心を持つ。

| シート名（定数） | 実際のシート名 | 用途 |
|---|---|---|
| `SHEET_HONBUN` | `原本` | 実データ入力・読み取り対象 |
| `SHEET_KINYUREI` | `記入例 `（末尾半角スペースあり） | ヘルプ表示用、読み取り専用 |
| `SHEET_HENKOU_REKISHI` | `変更履歴` | コピー対象外 |

テンプレートからのコピー対象は`原本`・`記入例`の2シートのみ（`_SHEETS_TO_COPY`）。`変更履歴`はコピーしない。

## 6.2 OneDriveアクセス方式（実装済み）

> **概要（`adapters/onedrive_adapter.py`）**：OneDrive（共有URL経由）とのファイル入出力を担うアダプター。「フォルダの存在確認」「フォルダ作成」「ファイルの存在確認」「ダウンロード」「アップロード」など、限られた操作のみを外部に公開し、呼び出し側（`attendance_service`等）はGraph APIの認証・エンドポイントの詳細を一切意識しなくてよいようにする。Graph API用の環境変数が揃っていない場合は、ローカルディレクトリを疑似OneDriveとして扱うフォールバック実装（`_local_*`関数群）へ自動的に切り替わる。

- **技術方式**: Microsoft Graph API の `/shares` エンドポイントを使用（`onedrive_adapter._get_root_drive_item()`）。
- **認証方式**: クライアントクレデンシャルフロー（`onedrive_adapter._get_access_token()`）。取得したアクセストークンはプロセス内でキャッシュし、有効期限の60秒前から再取得する（`_TOKEN_EXPIRY_BUFFER_SECONDS`）。
- **権限**: `Files.ReadWrite.All`（アプリケーション権限、要管理者同意）。
- **共有URLのエンコード**: `urlsafe_b64encode`で`"u!" + base64url（パディングなし）`形式にエンコードする（Microsoft Graph公式仕様準拠）。
- **ルートdriveItemのキャッシュ**: `ONEDRIVE_SHARE_URL`が指すフォルダの`driveId`・`itemId`は、プロセス起動中に一度解決したらキャッシュする（共有リンクの解決結果は実行中変化しない前提）。
- **パス解決**: 呼び出し側は共有ルートからの相対パス（例：`"202608/【会社名】勤務実績管理表_202608_山田太郎.xlsx"`）のみを意識すればよく、`driveId`・`itemId`の解決はすべて`onedrive_adapter`内部（`_resolve_path_to_item`、パス構成要素を1階層ずつ`_find_child_by_name`でたどる）に隠蔽される。
- **フォールバック**: `ONEDRIVE_TENANT_ID` / `ONEDRIVE_CLIENT_ID` / `ONEDRIVE_CLIENT_SECRET` / `ONEDRIVE_SHARE_URL`のいずれかが未設定の場合、`_graph_api_configured()`が`False`を返し、`ONEDRIVE_LOCAL_ROOT`（デフォルト`./data/onedrive_local`）を使ったローカル疑似OneDrive実装（`_local_*`関数群）に自動的にフォールバックする。本番運用では4環境変数すべてを設定すること。

## 6.3 OneDrive Adapter 公開インターフェース

外部には以下の操作のみを公開する（Graph API実装・ローカル疑似実装のいずれでも同一シグネチャ）。

```python
folder_exists(folder_name) -> bool
ensure_folder(folder_name) -> None       # 存在すれば何もしない（冪等）
file_exists(relative_path) -> bool
download_file(relative_path, local_dest_path) -> None
upload_file(local_source_path, relative_path, overwrite=True) -> None
list_files(folder_name) -> list[str]
get_last_modified(relative_path) -> Optional[str]   # ETag。8.4節参照
```

- `ensure_folder`：Graph API実装では、フォルダ作成時に`@microsoft.graph.conflictBehavior: "fail"`を指定した上でHTTP 409（競合）を許容し、他リクエストが同時に同名フォルダを作成した場合もエラーとしない。
- `upload_file(overwrite=False)`：アップロード先に既にファイルが存在すれば何もしない（先着優先、同時アクセスによる重複生成対策）。`overwrite=True`は無条件に上書きする（勤怠データ保存時に使用）。

## 6.4 冪等性
- フォルダ・ファイルの存在確認を行い、存在しない場合のみ作成する。
- 複数ユーザーが同一の未作成月へほぼ同時にアクセスしても、`ensure_folder`のHTTP 409許容・`upload_file(overwrite=False)`の先着優先により、最終的に1つのフォルダ・1つのファイルに収束する。

## 6.5 Excelテンプレート
- コピー対象：`原本`、`記入例`。`変更履歴` はコピーしない。
- テンプレートファイルの相対パス：`{COMPANY_NAME}勤務実績管理表_テンプレート.xlsx`（`attendance_service.get_template_relative_path()`）。

## 6.7 Excel書き込み方針
- **書式の保持**: 保存時は対象セルの`.value`のみ更新。罫線・条件付き書式・数式を維持する（`excel_adapter.write_day_cell`）。行・列の挿入削除やシート全体の再構築は行わない。
- **時刻データの変換**: フロント側で受け取った`H:MM`形式の文字列は、`_parse_time_input_text`で`(時, 分)`タプルへパースされ、`excel_adapter.time_tuple_to_excel_time()`で`datetime.time`オブジェクトに変換してセルへ直接代入する。読み取り時は`excel_adapter.excel_string_to_time_tuple()`で逆変換する。
- **保存直前の最終防御チェック**: `write_day_cell`内部で`_validate_time_tuple_format()`を呼び、`time_tuple_to_excel_string()`で生成した文字列が`validate_excel_time_string()`（正規表現）に一致するかを確認する。

## 6.8 自動計算項目・合計欄のPython側再計算

Excelの数式キャッシュ値は、`openpyxl`で`.value`のみを書き換えて保存した直後は再計算されず古いまま残る（Excelアプリで開くまで数式が評価されないため）。この「保存直後の表示ズレ」を避けるため、以下の項目はExcelの数式キャッシュを読まず、Python側で計算し直す。

- **日次自動計算項目**（`excel_adapter.calc_auto_values`）：休憩時間1・実働時間・超勤・休日出勤・深夜。休憩時間2・3は現時点では自動計算対象外で、読み取った入力値をそのまま使う。
  - 休憩時間1：始業〜終業と休憩時間1の開始・終了（ヘッダー領域G19・H19）の重複時間として算出。半休（午前半休／午後半休）の場合は0とする。
  - 実働時間：終業−始業−（休憩1+休憩2+休憩3+離業）。
  - 超勤：実働時間−所定労働時間（ヘッダー領域G11）。半休の場合は0、休日出勤の場合は算出しない（`None`）。
  - 休日出勤：休暇種類が「休日出勤」の場合のみ実働時間をそのまま転記。
  - 深夜：終業が深夜開始時間（ヘッダー領域D10）を超える場合のみ、終業−深夜開始時間。
- **月末合計欄**（`attendance_service._calc_totals`）：Excel原本シート42・43行目相当。日別`DayEntry`（既に自動計算済み）から再集計する。
  - Q42相当（定時）＝AF42相当（実働合計）－AI43相当（超勤+休日出勤合計）
  - AI43相当（超勤+休日出勤合計）＝AI42相当（超勤合計）＋AL42相当（休日出勤合計）
  - その他（休憩1〜3合計・離業合計・実働合計・超勤合計・休日出勤合計・深夜合計）は該当列の単純合計。

この再計算処理は、`load_attendance`（原本シート）と`load_example`（記入例シート）の両方で共通して使われる（`_load_attendance_from_sheet`）ため、記入例のプレビューも原本のプレビューと完全に同じ精度で表示される。

# 7. バリデーション設計

## 7.1 基本方針

入力時と保存時の二重チェックとする。

```text
画面入力時
 ↓
行単位チェック（リアルタイム）
 ↓
保存時
 ↓
月全体チェック（validate_all）
 ↓
保存直前に再チェック（ロック状態）
```

## 7.2 主なルール

`validation_service.validate_entry()`が判定する。

### VAL-01
日付が存在しない行には休暇種類を入力できない。

### VAL-02
日付が存在しない行には始業・終業時間を入力できない。

### VAL-03
以下の休暇区分（`FULL_DAY_LEAVE_TYPES`）では始業・終業時間を入力できない。

```text
有休
長期連休
特別休暇
欠勤
振替休暇
```

逆方向（既に時刻が入力済みの状態から、上記いずれかの休暇種類へ変更する操作）も同一ルールで検知する。

### VAL-04
土日かつ休暇種類が未選択で、始業・終業時間が入力されている場合はエラー。

### VAL-05
土日でも休暇種類が選択されている場合は、VAL-04のエラー対象外とする。

例：
```text
土曜日 + 休日出勤
```
などは入力可能。

> VAL-04・VAL-05は実装上、`validate_entry`内で1つの条件式（`weekday in ("土","日") and not leave_type and has_start_or_end`）として統合実装されている。

## 7.3 UIによる予防

画面側（`01_attendance_input.py`・`02_admin_attendance_edit.py`）で、以下の場合に始業・終業・離業・自社工数内容の入力欄を`disabled`にする（`should_disable_time`フラグ）。

- 休暇種類が`FULL_DAY_LEAVE_TYPES`のいずれか（`is_full_day_leave`）
- 土日かつ休暇種類未選択（`is_weekend_without_leave`）

ただし、入力済みの時刻がある状態で休暇区分へ変更した場合は、入力欄を強制的に空にする（変更を禁止する）のではなく、行単位のエラー（`st.error`）として検出し、保存ボタンを無効化する形で防止する。

## 7.4 時刻形式

```regex
^([0-9]|1[0-9]|2[0-3]):[0-5][0-9]$
```

例：
```text
9:00    OK
9:30    OK
23:59   OK
09:00   不許可
24:00   不許可
9:60    不許可
```

画面側の入力は3.11節のサニタイズ処理を経てからこの正規表現でチェックされる。

# 8. 排他制御・ロック設計

## 8.1 基本方針
- 一般ユーザーとadminの編集可能状態を逆にする。
- **一般ユーザー**: 「ロックされていない月」のみ編集可能。
- **admin**: 「ロック中の月」のみ編集可能。
- この設計により、同一ファイルへの一般ユーザー・admin間の同時編集は構造的に発生しない。

## 8.2 一般ユーザー保存直前チェック

`attendance_service.save_attendance(actor_role="general")`が、保存操作の直前に`lock_service.is_locked()`で最新のロック状態を再取得する。ロック済み（`True`）であれば`LockedError`を送出し保存を中止する。画面側（`01_attendance_input.py`）は`LockedError`を捕捉し、`st.error`でメッセージを表示する。入力中の内容は画面上に残る（強制的な消去は行わない）。

## 8.3 admin保存直前チェック

同様に、`actor_role="admin"`の場合はロックが解除済み（`False`）であれば`LockedError`を送出する。adminが編集中に他画面（別タブ等）からロックが解除された場合を想定した保存直前の再チェックである。

## 8.4 admin間の排他制御（未実装事項）

要件定義書13.4節では、同一admin（1名運用だが複数タブ・複数端末からの操作を想定）によるロック状態・ユーザーマスタの同時更新に対し、保存直前の最新状態再取得による楽観的排他制御（更新前後での更新検知）を適用する方針が示されている。

`onedrive_adapter.get_last_modified()`（ETag取得）は関数として実装済みだが、**現時点でこの関数を呼び出す箇所はコード内に存在しない。** すなわち、ロック管理画面（SC-05）・ユーザー管理画面（SC-06）における「保存直前に最新状態を再確認する」楽観的排他制御は未実装であり、admin1名かつ複数タブ操作という限定的なシナリオでの競合は現状検知されない。16章「未確定事項」に記載する。

# 9. PDF出力設計

## 9.1 出力方式

`pdf_service.py`が担う。**LibreOffice経由の変換方式**を採用する。

- 当初検討していた「reportlabによる自前描画」方式（案B）は、罫線・列幅・数式結果の再現が構造的に困難で、自動計算列・合計欄など数式に依存する項目が空白になる問題が繰り返し発生したため不採用とし、サーバー環境にLibreOfficeを導入して「Excelファイルをheadlessモードで実際に開いてPDF変換する」方式（案A）に切り替えている。
- 出力範囲：`原本`シートの`J1:AQ50`をA4縦1枚に収める。
- 複数名選択時はZIP化する（1ユーザー1PDFファイル、結合はしない）。
- OneDrive・サーバーいずれにも永続保存しない（一時ディレクトリを使い捨てる）。

## 9.2 変換処理の詳細

1. `attendance_service.get_or_create_monthly_file()`＋`load_attendance()`で対象データを取得する。
2. 一時ディレクトリ内に元ファイルのコピー（`print_ready.xlsx`）を作成し、**このコピーに対してのみ**以下を行う（元のOneDriveファイル・ローカルキャッシュには一切書き込まない）：
   - `原本`シート以外（`記入例`等）を削除する。LibreOfficeの`--convert-to pdf`はブック内の全シートを変換対象にしてしまうため、確実に原本シートのみのPDFにするための処置。
   - 印刷範囲を`J1:AQ50`に設定し、用紙をA4縦・余白0.3インチに設定し、`fitToWidth=1`・`fitToHeight=1`で1ページに収める。
   - **C列（曜日）をPython側で計算済みの日本語表記（`DayEntry.weekday`）で直接上書きする。** Excel側の数式`=TEXT(B14,"aaa")`はLibreOfficeのロケール設定に依存して英語表記（`Mon`等）になってしまう問題への対策。
3. `subprocess.run`で`soffice --headless --norestore --convert-to pdf --outdir <work_dir> <xlsx_path>`を実行する。コマンド名は`soffice`→`libreoffice`の順にPATH上の存在を確認して決定する（`_find_soffice_command`）。タイムアウトは60秒。
4. 生成された同名`.pdf`ファイルをバイナリとして読み込み、一時ディレクトリごと破棄して返す。
5. 複数名選択時は、上記処理をユーザーごとに繰り返し、`zipfile.ZipFile`でメモリ上のバッファにZIP化する。

# 10. 認証・パスワード設計
- bcryptによるハッシュ化（`auth_service.hash_password` / `verify_password`）。
- IDが存在しない場合とパスワードが違う場合でエラーメッセージを区別しない（セキュリティ方針）。
- パスワードポリシー：8文字以上64文字以内、半角英大文字・英小文字・数字・一部記号（`! # $ % & * + - . / : = ? @ ^ _`）のみ使用可能、英大文字・英小文字・数字のうち2種類以上必須。
- adminアカウント（`employee_id="admin"`）は初回起動時に`INITIAL_ADMIN_PASSWORD`（環境変数、デフォルト`"ChangeMe123"`）で1件だけ投入される。運用開始後は速やかにSC-07またはDB直接更新で変更することを推奨する。

# 11. エラーハンドリング方針

## 11.1 基本方針

画面にはユーザーが理解できるエラーを表示する。内部例外の詳細をそのままユーザーへ表示することは避ける（ただしPDF生成エラー等、一部画面では`str(e)`をそのまま表示している箇所があり、運用時のログ出力方針とあわせて要検討）。

## 11.2 主なエラー

| エラー | 対応 | 実装箇所 |
|---|---|---|
| OneDrive/ファイル取得失敗 | 読み込み・保存失敗を表示 | `OneDriveError` |
| Excel形式異常 | 管理者への連絡を案内 | `ExcelFormatError` |
| SQLiteエラー | システムエラーを表示 | `db_adapter` |
| バリデーションエラー | 行単位で表示し保存中止 | `validation_service.ValidationError` |
| ロック競合 | 保存中止、入力内容は保持 | `attendance_service.LockedError` |
| PDF生成失敗 | PDF生成失敗を表示 | `pdf_service.PdfConversionError`、`FileNotFoundError`（テンプレート未検出等） |

## 11.3 ログ

要件上、監査ログ機能は設けない。アプリケーションとして永続的な操作履歴・障害ログを保持しない。ただしDockerや実行環境が標準で出力する一時的なコンソールログ等は除く。

# 16. 未確定事項・今後の確認事項
- **admin間の楽観的排他制御の実装**：`get_last_modified()`（ETag取得）は実装済みだが、ロック管理画面・ユーザー管理画面の保存処理から呼び出されていない。同一admin（1名運用）が複数タブ・複数端末から同時操作した場合の競合は現状検知されない（8.4節参照）。実運用上のリスクの大きさを踏まえ、対応要否を判断する。
- **`User`データクラスの重複定義**：`auth_service.py`と`user_service.py`にほぼ同一の`User`データクラスが重複して存在する。統合の要否を検討する（5.10節参照）。
- **記入例シート名の末尾スペース**：`excel_adapter.SHEET_KINYUREI = "記入例 "`（末尾半角スペースあり）という実装上の制約がある。テンプレートファイル更新時にシート名の表記揺れがあるとエラーになるため、命名規則の明文化または実装側でのtrim対応を検討する（3.10節参照）。
- **Graph API 本番接続検証**：`/shares` エンドポイントを用いた実環境での挙動確認（大量データ・長時間稼働時のトークン更新・レート制限等）は未実施。
- **PDF出力の微調整**：実機でのフォント・印刷範囲の最終確認。
- **エラーメッセージの詳細度**：PDF出力画面等で`str(e)`を直接ユーザーに表示している箇所があり、11.1節の「内部例外の詳細を表示しない」方針との整合を要確認。

# 18. 設計上の重要ポイントまとめ
1.  **Streamlit一体型アプリ**として構築する。
2.  **画面・業務ロジック・外部連携を分離**する（`_pages/` / `services/` / `adapters/`）。
3.  **セッション管理の完全なクリア**（`st.session_state.clear()`）を徹底する。
4.  **ユーザー・ロック・設定はSQLite**で管理する。
5.  **勤怠データ本体はExcelファイル**で管理する。
6.  **一般ユーザーとadminの編集権限を構造的に排他的**にする（ロック状態の逆転）。
7.  **OneDrive連携はGraph API `/shares` とクライアントクレデンシャル**を用いる（実装済み、未設定時はローカル疑似OneDriveへ自動フォールバック）。
8.  **Excelの書式を崩さない**ため、保存時は`.value`のみ更新する。
9.  **自動計算項目・合計欄はExcel数式キャッシュに依存せず、Python側で再計算**する（保存直後の表示ズレ対策）。
10. **パスワードはbcryptでハッシュ化**する。
11. **PDFはLibreOfficeを利用**し、原本シート単独抽出・曜日列のPython値上書きにより、ロケール依存やシート混入の問題を回避する。
12. **Dockerで環境を統一**する。
13. **ページファイル名は英語**で統一する。
14. **時刻入力は H:MM 形式のテキストボックス1つ**とし、NFKC正規化によるサニタイズを行う（プルダウン方式は不採用）。
15. **admin間の楽観的排他制御は現時点で未実装**であり、今後の検討課題として明記する。
